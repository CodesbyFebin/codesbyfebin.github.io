thiserror vs anyhow: Choosing Error Handling by Crate Boundary

thiserror vs anyhow explained by crate boundary: typed errors for libraries, contextual errors for binaries, and conversion patterns that keep both happy.

The boundary rule, stated once

Ask one question: will someone write match against this error? If yes -- published crate, public module, service API -- the error is part of the interface and needs a named, stable, documented type: thiserror. If no -- a binary's main, a script, an internal tool -- the error is a report and needs context chains and a clean exit: anyhow. Mixing directions produces the two classic smells: libraries leaking anyhow::Error (callers reduced to string-matching, which breaks on wording changes) and binaries defining 40-variant enums nobody matches (ceremony without consumers, maintained forever out of habit).

thiserror: errors as API

Three API-hygiene rules keep thiserror enums honest: variants are semver surface (removing or repurposing one is a breaking change; adding is minor), messages may change freely but codes must not (clients match variants, humans read messages), and every variant carries exactly the data a caller needs to react -- a corruption offset invites recovery tooling, a bare "corrupt" invites a support ticket. Review error enums like public APIs because they are.

anyhow: errors as report

Context is where anyhow earns its dependency: each with_context adds the sentence a maintainer will need at 2 a.m. -- which file, which vkey, which stage. Two habits keep chains useful: attach context at the layer that knows the nouns (the verifier should not know filenames; main should not know FRI internals), and prefer lazy closures so formatting costs nothing on the happy path. The printed chain, outermost first, is your incident narrative; if reading it does not explain the failure, the contexts are decorating rather than informing.

Living at the seam

Real projects contain both halves, and the seam is one line: libraries return typed errors; binaries map them with .context() into anyhow at the boundary, preserving the typed variant for matching where reactions exist and the context chain for everything else. For services, add a third tier: an API-error enum (as in the axum tutorial) that maps typed domain errors to statuses while anyhow-style context flows to logs. The resulting layering -- typed domain errors, contextual application errors, mapped wire errors -- gives every audience exactly its format: code matches, operators read, clients parse.

Testing errors: the cheapest contract tests you own

Anti-patterns worth naming in review

  • String-matching errors: err.to_string().contains("timeout") -- breaks on rewording; add a variant or use source downcasting instead.
  • The catch-all enum variant: Other(String) accumulates until the type lies; prefer boxing a source error with #[source].
  • Context-less ? chains in binaries: technically anyhow, practically bare; the chain is the product.
  • Logging and returning: double-reporting confuses incident timelines; log at the boundary that handles, return everywhere else.
Can a library use anyhow internally?

Yes, inside private functions, as long as public signatures stay typed: convert before returning (map_err into your enum). The risk is drift -- internal anyhow strings tempting public variants -- so keep the conversion point single and tested; reviewers should see exactly one place where context chains become typed errors.

What about no_std or tiny binaries?

anyhow allocates; thiserror can be allocation-free with careful variants. For embedded or size-critical builds, prefer thiserror-styled enums everywhere and hand-rolled context (an enum carrying a &'static stage string), which keeps both matching and reporting without heap -- the pattern in tiny-verify's verifier, where error types cost bytes reviewers can count.

Should error enums implement PartialEq for tests?

Yes for thiserror types -- tests asserting exact variants are the cheapest API-contract tests you can write, and they catch accidental variant reuse during refactors. Skip it for payload-heavy variants by comparing discriminants via a helper; never test Display strings, which are prose and free to improve.
