Rust Struct Memory Layout and Padding: See What the Compiler Sees

Rust struct memory layout and padding: field reordering, repr(C), alignment math and the tools that show exactly what the compiler built for you.

The rules, with the arithmetic shown

Each field starts at an offset divisible by its alignment (u64: 8, u32: 4, references: 8 on 64-bit); struct alignment is its largest field's; size rounds up to a multiple of alignment. The classic waste: { a: u8, b: u64, c: u8 } occupies 24 bytes (7 pad after a, 7 after c); reorder to { b, a, c } and it is 16. At a million instances in a Vec, that reorder is 8 MB of cache-resident difference -- the cheapest performance win in the language, found by reading layout rather than profiling. Arrays and Vecs of structs amplify field order into cache-line geometry: hot fields straddling line boundaries double traffic in scan loops, which is why data-oriented redesigns (structure-of-arrays for scanned columns) beat micro-tweaks when flamegraphs show memory-bound plateaus.

Enums: niches, payloads, and the Box decision

An enum's size is its largest variant plus discriminant, unless niche optimization applies (Option<&T> stays pointer-sized by encoding None in the null niche). Consequence for design: one bloated variant bloats every value -- a rarely-taken Error(LargeContext) inside a hot Result taxes every Ok. The fix is Box on cold payloads (indirection costs one pointer and one allocation on the cold path only) or splitting the enum by frequency. Measure with the same discipline as everything here: size_of prints in tests pin expectations, and a CI assertion on size_of for hot types catches the commit that adds a field to the wrong variant -- layout regressions are silent in diffs and loud in cache misses.

Seeing layout: the tool ladder

The exploration/verification split matters: type-size prints answer "what is", while test asserts answer "what must stay" -- pin size_of and alignment for hot types and FFI structs, with a comment naming the cache-line budget, so layout becomes a reviewed contract rather than an emergent property. For FFI, repr(C) freezes layout against Rust's freedom to reorder (the default repr is explicitly unordered), and static asserts on offsets mirror the C header's expectations -- the two-sided pinning that keeps cross-language structs honest across compiler upgrades.

Patterns that earn their complexity

  • Field reordering: free, always first; group hot fields to share cache lines, cold metadata to trailing lines.
  • Structure-of-arrays for scanned columns: converts strided access into sequential streams; worth it when profiles show memory-bound loops, not before.
  • Arena indices instead of references: u32 handles halve pointer width and stabilize serialization; the arena pattern from the E0505 Q&A doubles as a layout tool.
  • SmallVec for short collections: inline capacity kills the allocation and the pointer chase for the common case; size it from measured length histograms, not guesses.

Each pattern trades indirection or flexibility for bytes and locality; the portfolio rule applies unchanged -- adopt with a benchmark row and a design-note sentence, because layout decisions without recorded reasoning revert silently during the next refactor, and cache misses do not file issue reports.

A worked intuition for reviewers: when a diff adds a field to a hot struct, ask three questions before approving -- does it preserve field ordering by temperature (hot fields still front-loaded), does it cross a cache-line boundary for the struct's common case, and does any enum variant grow because of it (taxing values that never carry the field)? Three seconds of questions per diff, applied consistently, prevent the layout regressions that benchmarks catch only quarterly; and when the answer is "yes, it costs, and we need it anyway", the design note gains one sentence recording the trade -- which is how a codebase accumulates layout wisdom instead of layout archaeology, one reviewed field at a time. Teach the three questions to every new contributor in their first layout review, and write the answers they discover into the type's doc comment beside the size assertion; a codebase where the cache-line budget lives in the same comment as the struct definition is a codebase where performance knowledge survives author departure, which is the only performance work that compounds instead of decaying.

Is repr(packed) ever right?

Almost never: packed structs misalign fields, forcing unaligned loads (slow or faulting on some ARM cores) and breaking references to fields (borrow a packed field and you get a compile error for good reason). On-disk or on-wire formats wanting dense encoding should serialize explicitly (byte buffers plus decode functions) rather than aliasing memory through packed types -- density is a format property, not a memory property, and conflating them buys bytes with faults.
