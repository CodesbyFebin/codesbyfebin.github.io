Setup: target, bindgen, and the two-crate shape

Interop: types that cross the boundary honestly

The wasm boundary speaks numbers and linear memory; everything richer is a convention you maintain. Primitives cross free; strings and buffers cross via bindgen-generated copies (allocate, write, free -- respect all three or leak); structured data crosses as JSON text or, at volume, as bincode bytes into a shared buffer you slice manually. The discipline: minimize crossings per operation (batch), keep lifetimes explicit (who frees what, documented at each export), and never pass Rust references out -- the borrow checker cannot see across the boundary, and the boundary is exactly where its guarantees stop. Serde at the edge converts "structured data" from a hope into a schema with tests, the same boundary thinking the systems guide applies to FFI generally, because wasm is FFI with a sandbox.

Size and load-time budgets, enforced in CI

  • wasm-opt -Oz after every release build; record before/after sizes in the build log.
  • Strip and avoid fmt-heavy panic paths: panic = "abort" plus a custom handler cuts tens of KB.
  • Budget gate: fail CI when gzipped module exceeds 200 KB (or your number) -- budgets without gates are wishes.
  • Lazy-load: fetch the module on first interaction for non-critical features; 1 s perceived becomes 200 ms actual for most sessions.

Measure load as users feel it: fetch plus compile plus instantiate, not bytes alone -- compile time scales with module size and device class, which is why the budget is gzipped bytes and a headless-browser instantiation assertion. The binary-size Q&A shares most of its toolbox here (strip, lto, dependency audits); wasm simply adds wasm-opt and the instantiate metric to the ledger.

Testing: headless browser as first-class target

wasm-pack test or plain wasm-bindgen-test in headless Chrome/Firefox runs your core logic where it will actually live: browser timers, memory limits, and JS interop included. Two test classes pay for the setup: interop round-trips (every exported function called with edge-case payloads, asserting the JS-visible contract) and performance floors (a benchmark assertion that instantiation stays under your budget on CI's browser, catching dependency bloat at merge time). Native unit tests keep covering the pure core at dev speed; the browser suite is the integration gate. This split mirrors the portless-handler testing philosophy from the axum tutorial: test at the boundary that users actually cross, and keep everything below it pure and fast.

Budget one evening for the browser-devtools profiling loop as well: the performance tab shows compile and instantiate cost separately from script execution, and the first time you watch a 400 KB module compile on a mid-range phone, your size-budget arguments in review stop being philosophical and start being photographic.

Threads, SIMD, and the honest limits

wasm-pack or raw cargo plus wasm-bindgen?

wasm-pack for libraries and teams: it wraps bindgen, wasm-opt, and packaging (npm-ready) coherently. Raw pipeline for apps with custom bundling or exotic targets, where pack's opinions fight yours. Both produce identical artifacts underneath; choose by how much packaging you want owned versus orchestrated, and pin whichever you pick in CI so glue-generation drift cannot reach production unreviewed.

How do I debug wasm in the browser?

Dev builds with DWARF (unoptimized, -g) give source-level breakpoints in Chrome/Firefox devtools; console_error_panic_hook turns Rust panics into readable JS console traces with Rust backtraces. Never debug optimized modules -- wasm-opt destroys the symbol-to-source mapping, and the time saved at build is repaid at 3 a.m. Keep a dev-wasm alias that builds unoptimized with hooks; debugging ergonomics are a build-target decision, not a browser extension hunt.

Can one wasm module serve native and web from the same repo?

Yes, via the two-crate shape: core compiles both targets, app crates diverge. Share tests too -- wasm-bindgen-test suites run core logic in browsers while native tests run the same cases on host, and divergence between the two runners is itself a signal (usually a time or randomness leak crossing the purity line). One repository, three targets, one purity rule: the core crate never asks what platform it is.
