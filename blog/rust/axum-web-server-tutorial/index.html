Axum Web Server Tutorial: Routes, State, and Graceful Shutdown

An axum web server tutorial: routers, extractors, shared state, middleware, graceful shutdown and testing handlers without binding a port in every test.

Router and extractors: let the signature be the documentation

Axum's core idea is that a handler's parameter list is its request contract: Path, Query, Json, State extractors deserialize and validate before your body runs, and rejection happens with correct status codes automatically. Design handlers so the signature reads like a sentence; anything you cannot express as an extractor is a design smell, not a missing feature.

Shared state: one Arc, many clones, zero locks in the hot path

Application state enters via .with_state(App) where App = Arc<AppState>; cloning the Arc per request increments its shared reference count and gives every handler immutable access plus interior mutability exactly where you placed it (a pool, an RwLock for config, an atomic counter). The rule that keeps latency honest: hot paths read atomics or lock-free caches; locks guard mutation that happens rarely (config reload, key rotation). If a handler needs a long lock, it needs a redesign -- usually a channel to a background task that owns the resource. State construction belongs in main, behind a fallible builder: a service that cannot assemble its state should exit at boot with a named reason, never serve degraded with a None checked per request.

Middleware: tracing, timeouts, and request ids

Layer order matters: trace first (so timeouts and rejections are logged), then timeout, then compression last. A global timeout via TimeoutLayer converts stuck dependencies into 504s instead of thread-pileups; the trace layer attaches a request id that your error envelopes echo, which is the difference between "user reports error" and "user reports error 7f3a". Keep custom middleware minimal -- every layer is code that runs on every request forever.

Errors: one envelope, typed sources, honest statuses

Define ApiError as a small enum implementing IntoResponse: variant determines status (NotFound 404, Validation 422, Upstream 502), body is a stable envelope { "error": code, "message": human, "request_id": id }. Convert library errors with thiserror at the source and map to ApiError at the boundary -- the pattern from the Rust systems guide's error-strategy section applied to HTTP. Never stringify library errors into 500 messages: that is how internals leak and how on-call loses the causal chain. Two envelope rules keep clients sane across versions: error codes are stable strings under semver (clients may match on them; messages are for humans and may change), and every error path includes the request id from the trace layer so support conversations start with a lookup instead of a guess. Add one test per variant asserting both status and envelope shape -- error contracts drift silently faster than success contracts, precisely because nobody exercises them happily.

Fallbacks, 404s, and method discipline

A production router needs an explicit .fallback(handler): axum's default 404 is a bare text body that breaks client parsers expecting your JSON envelope. Route unknown paths and mismatched methods into the same ApiError pipeline (404 and 405 respectively) so every response on the wire shares one shape -- clients that only ever parse one envelope are clients that never crash on surprises. Method discipline follows the same logic: define post routes with .method_not_allowed_fallback or rely on axum's 405, but always log the attempt; a spike in 405s for a given path is frequently the earliest signal of a misconfigured client or someone probing your API, and your trace layer already pays for that visibility whether or not you look.

Graceful shutdown and testing without ports

When should a handler spawn a background task?

When the work outlives the request's usefulness: proof generation, report rendering, webhook fan-out. Return an accepted status plus a job id immediately, run the work in a tokio task owned by state (not by the request), and expose status via a job endpoint. Spawning without an owner is how orphan tasks survive shutdown and double-execute after restarts.

Is axum's default 2 MB body limit enough?

For JSON APIs, yes -- raise it deliberately with DefaultBodyLimit per route when you must accept uploads, and pair any raise with validation and a streaming parser. A global raise to "fix one route" silently turns every endpoint into a memory-exhaustion surface; scoped limits keep the blast radius where you intended it.

How do I version an axum API without route chaos?

Prefix routers (/v1, /v2) built from shared handler modules, and deprecate by removal only after a logged-usage window: your trace layer already records which clients hit which prefix. Header-based versioning saves URLs but splits behavior invisibly; visible prefixes keep the deprecation conversation honest and the logs readable.
