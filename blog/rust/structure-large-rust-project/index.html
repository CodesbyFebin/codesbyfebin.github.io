How Should I Structure a Large Rust Project (Workspaces, Crates)?

How to structure a large Rust project: workspace layout, crate boundaries, feature flags, internal prelude crates and the CI rules that keep compile times sane.

The workspace spine

The rule that keeps the spine straight: core never depends upward or sideways, and defines traits that adapters implement (storage, clocks, randomness) so tests substitute fakes without frameworks. When a type wants to live in two crates, it belongs in the lower one or in proto; when a function wants IO inside core, it wants a trait instead. These two sentences resolve most architecture arguments in review, and the CI graph check (cargo-depgraph diffed against an allowed matrix) resolves the rest mechanically -- architecture as enforced property, the same philosophy the unsafe licensing applies to memory.

Feature hygiene and compile economics

Features multiply build matrices and surprise downstream users; the discipline: features add capability, never remove correctness; default features stay minimal in libraries and maximal in binaries; and every feature gets a CI job in the matrix (feature powerset sampled pairwise at minimum) because untested features are broken features discovered by consumers. Compile-time governance follows: keep crates under ~15k LOC or split (incremental rebuild granularity), avoid proc-macro dependencies in core (they rebuild the world), and watch cargo build --timings trends in CI comments on merge requests that move the top-five slowest crates -- compile time is a shared budget spent silently, and budgets need visible receipts.

Errors, versions, and crate boundaries as semver surface

Public crates in the workspace follow the error strategy from the thiserror/anyhow guide: typed enums outward, anyhow inside binaries, and proto types versioned with the same care as public APIs (they are). Internal crates may move faster under a workspace-wide semver policy ("internal crates: breaking changes allowed with whole-workspace migration in one commit"), which keeps velocity without lying to external users -- the two audiences get two contracts, explicitly named in CONTRIBUTING so contributors know which clock they are on. Binary crates pin everything; library crates expose MSRV tested in CI per the hygiene list from the systems guide.

Tests and docs at workspace scale

  • Unit inside crates, fast, no network; integration in tests/ composing real adapters against tempdirs; contract suites per proto version run against every implementation.
  • Doc tests on every public item of public crates; internal crates carry design notes instead (the note discipline from the systems guide, folder per crate, updated in the same PR as behavior).
  • Benchmarks live beside core with baselines in CI; performance regressions block merges at the layer where they are cheapest to fix.
  • Ownership map: CODEOWNERS per crate with named deputies -- the bus-factor practice from the mentorship program applied to directories.
Monorepo with non-Rust components: still workspaces?

Yes, nested: the Rust workspace lives under a repo root that also holds infra, docs, and other languages, with the root owning CI orchestration and the workspace owning Rust policy. Cross-language contracts (proto schemas, JSON envelopes) live at root with contract tests both sides run -- the boundary file is the interface, and interface files with two-sided tests are the only cross-language agreements that survive reorganizations.

How do I keep prelude crates from becoming junk drawers?

Admission rule: prelude accepts only re-exports and conversion glue used by three or more crates, reviewed quarterly with usage counts; anything else returns home. The junk-drawer failure mode is real and terminal (prelude becomes the dependency of everything and the responsibility of nobody), so the three-crate threshold plus quarterly prune is not bureaucracy -- it is the drawer's lock, and the usage count is its key.
