Why Is My Rust Program's Memory Usage Higher Than Expected?

Why Rust memory usage exceeds expectations: allocator arenas, Vec overcapacity, monomorphization duplicates and the profiling stack that finds the real owner.

Attribution before accusation

The four owners, with their signatures

  • Allocator arenas: RSS plateaus above heap; malloc_trim or jemalloc purging drops it instantly; fix by tuning trim thresholds or accepting the plateau with a documented ceiling (capacity planning, not pathology).
  • Overcapacity: Vec growth doubling leaves up to 50% slack per container; signatures are millions of small Vecs or a few giant ones with reserve() guesses; fix with shrink_to_fit at stable points, exact reserves from measured lengths, or SmallVec inline buffers.
  • Binary bloat page-cache: RSS includes executed binary pages; a 200 MB monomorphized binary "uses" tens of MB just running; verify via size and bloat crates per the size Q&A; fix by de-generifying hot generics or splitting binaries.
  • True leaks: monotone growth in heap-profile live bytes with stable traffic; in safe Rust almost always cycles (Rc/Arc parent-child) or global registries (metrics labels, interners, listener lists) growing with cardinality; fix by Weak back-refs, bounded registries, and cardinality alerts.

The cardinality trap: leaks by design

A repeatable investigation workflow

  1. Reproduce with a traffic replay at 10x scale for 30 minutes; leaks that hide in production surface fast under amplification.
  2. Graph RSS, heap-allocated, and allocator-mapped on one panel; classify shape (plateau versus climb).
  3. Heap-profile the climb (or dhat a repro binary); export top-20 owning stacks with cumulative bytes.
  4. Name the owner class from the four; apply its fix; re-run replay and require the graph, not the anecdote, to change.
  5. Pin the regression: a memory-budget test (peak RSS assertion in the replay harness) joins CI beside the benchmark baselines.
Does async make memory profiling harder?

Slightly: task stacks are heap futures (small) but per-task buffers multiply by concurrency, so "which task owns this" needs task-id tagging in allocation profiles (jemalloc prof with thread=task mapping approximates it). The bigger async-specific owner is unbounded queues -- channels without caps are memory growth wearing concurrency's clothes, and the bounded-channel rule from the tokio tutorial is a memory policy as much as a flow policy.

Is swapping ever acceptable for a Rust service?

As shock absorption yes (zram or low swappiness), as capacity no: swapped hot paths stall latency unpredictably and PSI alerts should fire before swap-in becomes routine. The exception class is batch workers with cold phases, where swapping idle pages is exactly the economy it exists for -- know which shape your service is, and let the pressure metrics from the monitoring guides tell you when the shape changed.

How do I set memory limits for containers running Rust?

From measurement: peak RSS in the replay harness plus allocator plateau headroom (typically 1.2-1.5x), never from the sum of cache budgets on paper. Set the container limit at that number and alert at 80% of it; OOMKilled events are the limit telling you the measurement was wrong, and each one should update the replay harness rather than just the limit -- limits without replays drift, and drifted limits kill at the worst minute.
