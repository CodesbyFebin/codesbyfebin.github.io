REST API in Rust with Axum and Serde: Validation Done Right

REST API in Rust with axum and serde: request validation, error envelopes, versioning, pagination and content negotiation done the idiomatic way.

The wire contract: serde attributes as documentation

Three attribute habits pay permanently: deny_unknown_fields on create/update bodies (typos surface immediately; versioning tolerance handled explicitly at the envelope, not by swallowing), rename_all = "camelCase" decided once per API style and enforced by contract tests, and defaults only where semantics genuinely default (security bits yes, permissions never). The validate method returns field-level issues -- path, code, message -- which the error envelope from the handler-errors guide serializes verbatim, so clients render your validation in their forms without parsing prose.

Responses: shapes, not dumps

Serialize dedicated view structs, never ORM or domain internals: ProofView carries id, status, vkey hash, created-at, and links -- not memory addresses, not internal enums with repr drift. Version views alongside domain types and convert explicitly; the conversion layer is where deprecation fields live ("legacy_id" for two versions, then removed with a changelog entry). For collections, envelope consistently: {items, next_cursor, total?} with cursor pagination default (offset pagination is a denial-of-service vector on large tables and a correctness hazard under writes -- cursors are slightly harder to build once and correct forever).

Versioning and content negotiation, chosen deliberately

Prefix versioning (/v1) for breaking shape changes; additive changes ship unversioned with fields defaulting absent on old clients. Content negotiation earns its complexity only when multiple representations are first-class (JSON plus CBOR for constrained clients, say); otherwise a single JSON grammar with stable codes, per the envelope guide, keeps SDK generation trivial. Log version hits per client key from day one: the deprecation conversation becomes a query ("three keys still on v1, all internal") instead of a broadcast email, and sunsets land on evidence -- the same orphan-pruning discipline the edge-config and tool-registry reviews apply elsewhere in this portfolio.

Contract tests: the API's real specification

  • Schema round-trips: every view struct serializes to golden JSON snapshots (codes and shapes, not volatile fields).
  • Rejection matrix: unknown fields, wrong types, oversize bodies, missing required -- each asserts status plus envelope codes via portless Router::call.
  • Validation vocabulary: each validate rule has one passing and one failing case producing the documented FieldIssue code.
  • Pagination behavior: cursor stability under concurrent inserts (a property test with shuffled writers), because pagination bugs surface as duplicated invoices, not as test failures.
Should errors include validation details for auth failures too?

No: authn/authz failures return minimal envelopes (401/403 with a stable code and request id) without field-level detail -- detailed rejection vocabularies on auth endpoints are enumeration oracles. Validation detail belongs to 422s on authenticated, schema-checked bodies; the asymmetry is deliberate and documented in the API guide so client authors stop asking.

How do I handle large uploads without buffering?

Stream into a temp target with size caps enforced at the byte counter (not post-hoc), validate headers (content hashes where clients provide them), and commit atomically on completion; return 413 the moment caps trip mid-stream so clients abort early. Pair with the body-limit reasoning from the axum tutorial: global defaults stay small, upload routes raise deliberately with their own quotas and journals -- capacity policy as routing policy.

Is it worth adding HATEOAS links?

Selectively: "next_cursor", "self", and state-transition links (approve, cancel) genuinely reduce client coupling and version pain; full HATEOAS graphs rarely earn their generator complexity outside long-lived public APIs with third-party SDKs you cannot update. Ship the three pragmatic links, name them in the contract tests, and revisit when a second consumer ecosystem appears -- evidence-driven adoption, the portfolio's recurring refrain.
