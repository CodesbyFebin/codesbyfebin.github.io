How Do I Profile Rust Code Without Changing Its Behavior?

How to profile Rust code without changing its behavior: perf, samply, flamegraphs, criterion baselines and the pitfalls of profiling optimized builds.

Sampling first: perf and samply

Sampling's contract is honesty under real conditions: no recompiled instrumentation, no perturbed inlining, the exact shipped binary doing its actual job. Read flamegraphs top-down for wide plateaus (your hot functions) rather than tall spikes (deep but cheap call chains); the plateau that surprises you is the finding, and the one you expected is the control. Keep the SVGs: a profile library per release makes regressions attributable to the commit that widened a plateau, which is capacity archaeology no benchmark suite alone provides.

Hardware counters: when the flamegraph lies by omission

CPU-bound plateaus with healthy-looking code usually mean memory: perf stat -e cache-misses,LLC-loads,branch-misses quantifies the suspicion; high miss rates redirect you from "optimize this function" to "change this layout" -- struct field order, boxing cold enum variants, swapping pointer-chasing trees for Vec iteration, the layout toolbox from the cluster's memory-layout shelf. Branch misses point at unpredictable conditionals in hot loops: branchless reformulations or sorted inputs convert them into predictable streams. Counters turn flavor arguments ("I think it's allocation") into numbered ones ("LLC-misses per item doubled in this commit"), which is the only dialect review comments should speak.

Micro changes: criterion with baselines and statistics

For function-scale decisions, criterion's model -- warmups, outlier classification, baseline comparison -- beats hand-timed loops by removing the two lies humans tell themselves (warm-cache first runs and selective memory about variance). Workflow: baseline before touching code, change one thing, compare with --load-baseline, and record the delta beside the commit. Guard against benchmark drift by pinning inputs in-repo and re-running the suite on CI weekly; benchmarks rot like tests, but silently, because nobody's build fails when a bench starts measuring the allocator instead of your algorithm -- a rot class the slow-release Q&A meets from the build side.

Async and concurrent code: scheduler-aware views

Sampling shows CPU, but async latency lives in waits: pair perf with tokio-console's task views (poll counts, idle-forever detection) and tracing timelines for request-shaped questions. For contention, lock statistics (wait time per acquisition) from tracing spans beat inference; a mutex held across an await announces itself as worker-starvation plateaus in the runtime's poll functions, the signature catalogued in the tokio tutorial. The general rule holds: choose the instrument that sees the resource you suspect -- CPU samples for cores, counters for memory hierarchy, scheduler views for waits, and never diagnose one resource's illness with another's thermometer.

Habits that keep profiling honest

  • Profile release builds only; debug profiles measure the compiler's pessimism, not your code.
  • Quiesce the box: close browsers, pin governors, note thermals -- the slow-LLM Q&A learned the same lesson at bigger wattages.
  • One change per measurement; interactions between "optimizations" are where false confidence breeds.
  • Write the finding, not just the fix: the design note's benchmark paragraph is what stops the next engineer from reverting you blind.

Profiling is empiricism applied to your own code: samples are observations, counters are measurements, baselines are controls, and notes are publication. Teams that ritualize all four stop arguing about performance entirely -- the arguments become experiments, and experiments, unlike opinions, terminate.
