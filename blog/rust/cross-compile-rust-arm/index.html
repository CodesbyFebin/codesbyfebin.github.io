Three toolchain routes, ranked by surprise-count

  1. zig as linker + sysroot (cargo-zigbuild): hermetic, no containers, handles glibc-version targeting flags (--target aarch64-unknown-linux-gnu.2.28) so old fleets keep working; fewest moving parts on CI runners.
  2. cross-rs containers: mature images per target with matching C toolchains; best when C dependencies are heavy (openssl, libpcap) and you want the container's package manager.
  3. distro packages (gcc-aarch64-linux-gnu + rustup target): fine on Linux CI, brittle on macOS hosts and for exotic targets; keep as the fallback, not the default.

C dependencies: where cross-builds actually die

Pure-Rust crates cross-compile silently; the failures concentrate where cc-rs shells out to a C compiler that defaults to host architecture. Fixes in order: ensure the target C compiler is on PATH under the names cc-rs expects (TARGET_CC env), prefer vendored features (openssl = { features = ["vendored"] }) so builds carry their own C source, and pin C dependency versions in the lockfile because upstream build-script changes love breaking cross environments mid-quarter. When a build script still misbehaves, read its output with -vv: build-script logs name the exact compiler invocation that failed, converting "cross build broken" into "missing aarch64 pkg-config target" in one screen -- the same read-the-exact-error discipline the cluster's compiler-suggestions Q&A preaches for rustc itself.

Verification: file, ldd, qemu, and the CI gate

Static musl or dynamic glibc for containers?

Musl-static for distroless/scratch images and maximum portability; gnu-dynamic when you need glibc NSS behavior (LDAP/AD resolution, certain DNS setups) or dlopen plugins. The DNS caveat matters operationally: musl's resolver historically ignores some resolv.conf options; if your deployment leans on exotic DNS, test name resolution inside the actual container, not on your laptop.

How do I keep cross builds cached in CI?

Cache by (target, lockfile-hash, toolchain-version) including the C toolchain identity (zig version or cross image digest) -- C dependencies rebuild when the linker changes even if Rust sources do not. Split caches per target to avoid eviction storms across your matrix, and warm them weekly so Monday's pipeline does not rediscover openssl from source in front of an audience.

Are ARM builds slower at runtime than x86 for my workload?

Per-core, typically 10-30% behind current x86 on scalar Rust workloads; ahead on watts and often on price-performance at fleet scale. Cryptographic kernels with ARM crypto extensions (SHA2, AES) can flip the comparison entirely when the crates enable them -- check the feature flags, because a missed sha2/asm-style feature is silently leaving half the board unused, a measurement the profiling Q&A's counter workflow surfaces in minutes.
