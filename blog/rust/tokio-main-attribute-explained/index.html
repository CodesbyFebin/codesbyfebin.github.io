What Exactly Does the tokio::main Attribute Do?

What #[tokio::main] actually does: macro expansion, runtime flavors, worker threads, and when to construct the runtime manually for embedded or test use.

The expansion, line by line

Three consequences follow directly. Worker count defaults to logical cores -- override with worker_threads(n) when your workload is IO-heavy on a many-core box (fewer workers, less stealing) or when co-tenanting. Dropping the runtime cancels spawned background tasks at main's end: daemons that "finish early and lose the shutdown journal flush" met this line, and the fix is joining handles inside block_on rather than racing the drop. block_on is synchronous: the thread running main is not a worker; parking it in a std call blocks nothing but itself, a distinction that dissolves half the confusion in runtime-nesting errors.

Flavors: current_thread, multi_thread, and why tests differ

#[tokio::main(flavor = "current_thread")] builds a single-threaded runtime: deterministic task ordering (excellent for reproducing races in tests), minimal resources (excellent for embedded-ish or per-request runtimes in FFI), and a hard rule -- any blocking call starves everything, since there is no other worker to absorb it. Multi-thread is the service default. Unit tests usually want #[tokio::test] (current_thread by default, fresh runtime per test, no cross-test interference); integration tests that exercise real concurrency opt into multi-thread explicitly. The classic panic "Cannot start a runtime from within a runtime" is this taxonomy enforcing itself: an attribute-made runtime already exists on your thread, and block_on inside it is a scheduling paradox the library refuses to schedule.

When to construct runtimes manually

  • FFI/embedded hosts: a C main or GUI loop owns the thread; build the runtime, keep the handle, drive it with handle.block_on or spawn from callbacks.
  • Multiple runtimes: isolating a latency-critical pipeline from bulk work (separate worker pools, separate budgets) -- an advanced shape, justified by measurement, documented per runtime.
  • Graceful shutdown choreography: main builds the runtime, spawns supervisors, and block_on's a shutdown coordinator rather than the service future, so drain order is explicit code instead of drop-order luck.

In all three, the attribute's convenience becomes a liability it was never designed to carry; writing the Builder by hand is ten lines that say exactly what your process topology is -- topology as code, the same philosophy the systems guide applies to ownership and the fleet applies to manifests.

Gotchas that earn their paragraph

Nesting: never call block_on inside an async fn (use spawn_blocking for sync work, join handles for child results). Panics: a panicking task does not kill the runtime; it kills the task and poisons its JoinHandle -- supervisors must watch handles or panics vanish into logs. Shutdown ordering: tasks holding resources should observe cancellation via select/shutdown tokens, because runtime drop is abrupt by design; the graceful-shutdown pattern in the tokio tutorial is the canonical fix. And environment variables like TOKIO_WORKER_THREADS exist but config-in-code beats config-in-environment for topology, because code is reviewed and environment is discovered -- usually during the incident it caused.

Does #[tokio::main] cost anything at runtime?

Nothing beyond what the explicit Builder does -- it is compile-time expansion, zero steady-state overhead. The only "cost" is cognitive: defaults hidden behind punctuation. Teams burned by defaults (worker counts on 128-core boxes, drop-time task cancellation) adopt explicit Builders in services as policy, keeping attributes for examples and tests where defaults are the point.

Can I run tokio runtimes inside WASM or browsers?

Not the threaded runtime: wasm32-unknown-unknown has no threads or blocking primitives; tokio's current_thread flavor partially ports with wasm-bindgen-futures driving the wake loop, but most browser-side async uses wasm-bindgen-futures or js-sys promises directly. The honest map: tokio owns servers and native clients; browsers own their own event loop, and code shared between them should stay runtime-agnostic pure logic -- the two-crate shape from the wasm guide.

Why does my #[tokio::test] pass alone but fail in suite runs?

Almost always shared external state (ports, files, env vars) rather than runtime interference -- each test gets a fresh current_thread runtime, but not a fresh world. Isolate with per-test tempdirs and ephemeral ports (bind :0), and reserve env mutation for serially-run tests (a serial feature or a mutex guard). Flaky suites train teams to ignore red; ignoring red is how green becomes meaningless.
