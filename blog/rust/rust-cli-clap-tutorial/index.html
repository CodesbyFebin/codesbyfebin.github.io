The derive struct is the specification

Three derive habits pay immediately. Put real prose in doc comments -- the generated --help is your documentation's front page and your only guaranteed-read document. Push validation into value_parser functions (existing_file, range checks, enum parses) so impossible states never reach business logic. And keep the struct dumb: parsing produces data, main dispatches, and every branch is unit-testable by constructing the struct directly -- the testing trick at the end of this guide.

Layered config: flags over env over file

One more source deserves mention because it arrives late in every project's life: persisted user defaults (~/.config/tool.toml). Fold it between file and env, print it in the effective-config dump with its source tag, and provide --no-config for reproducible runs in scripts and CI -- the flag that disables configuration is itself a configuration decision, and operators will need it on their worst day, when the runbook says "run exactly this" and the environment must be made silent. Test the fold too: a table-driven test with env, file, and flags set in conflicting combinations is thirty lines and keeps the priority contract true forever, which is more than can be said for any口头 convention -- or for any convention at all, once the original author has moved teams.

Derive or builder API?

Derive for anything with a stable shape: less code, help text colocated, completions free. Builder when the command surface is dynamic (plugin-registered subcommands) or generated from metadata. Mixing is fine -- a derive struct can embed a builder-constructed subcommand -- but pick per binary, not per flag, or the codebase grows two dialects.

How do I handle long-running subcommands and Ctrl-C?

Install a ctrl-c handler that flips an atomic and let work loops check it at safe boundaries, printing a one-line "cancelled, state saved" to stderr before exit code 130. For tokio-based subcommands, wire the same atomic into the runtime's shutdown signal as in the async tutorial; users forgive cancellation instantly and never forgive lost partial work.

Should flags accept JSON for complex inputs?

Only alongside typed flags, never instead: --filter kind=stark,size>1mb stays discoverable and completable, while --filter-json serves scripts with real structure. Validate both into the same internal predicate type so behavior cannot diverge, and document the JSON schema in the help footer -- dual interfaces with one semantics beat one interface with two audiences arguing.
