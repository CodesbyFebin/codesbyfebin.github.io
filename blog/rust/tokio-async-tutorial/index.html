Tokio Async Rust Tutorial: Tasks, Channels, and Backpressure

A tokio async Rust tutorial: tasks versus threads, channels and backpressure, timeouts, cancellation safety and the debugging tools for stuck runtimes.

Tasks versus threads: choose by what blocks you

A task is a state machine plus a wakeup; a thread is a stack plus a kernel object. Tasks cost hundreds of bytes and switch at await points; threads cost megabytes and switch at the kernel's pleasure. The selection rule is about blocking, not count: if the work waits on IO or timers, tasks win by orders of magnitude; if it computes for milliseconds at a time, threads (or spawn_blocking) win because a computing task never yields and starves its siblings on the same worker. The canonical sin is calling blocking APIs inside async fn -- std::fs, std::thread::sleep, a synchronous HTTP client -- which turns one slow operation into a whole-core outage. Wrap it: spawn_blocking exists precisely to exile such calls, and clippy's async lint set catches most escapes in CI.

Channels and backpressure: the design decision in disguise

An unbounded channel is a memory leak with an API: fast producers and slow consumers converge on OOM as certainty. The bounded channel's send().await is backpressure -- producers pause when the buffer fills, and the pause propagates to whatever feeds them, which is exactly how flow control should feel in a well-designed system. Choose the bound from measurement (p99 burst minus consumer drain rate), alert on saturation percent, and treat a permanently full channel as a capacity incident, not a tuning knob to widen.

Timeouts and cancellation safety

Every await that touches the outside world needs a ceiling: tokio::time::timeout around connects and reads, deadlines threaded through request contexts, and -- the part everyone forgets -- cancellation-safe internals. A future is cancellation-safe when dropping it mid-await leaves no state corrupted: recv() on channels is; a half-finished read-modify-write across two awaits is not. Audit by asking, per await: "if this future is dropped right here, what invariants hold?" Where the answer is "none", wrap the section in a guard or move it to a task that owns its state to completion. Timed-out provers that keep running in the background are how "stateless" services develop CPU debt, the same orphan-process discipline the MCP server guide enforces at its executor boundary.

Shutdown: the feature that proves the design

Graceful shutdown is where async designs show their seams: signal handler flips an atomic, listeners stop accepting, in-flight tasks drain under a deadline, channels close so consumers exit their loops, and JoinHandles are awaited -- in that order, every time. Services that skip the drain step lose in-flight proofs on every deploy; services that skip the deadline hang forever on a stuck task and get SIGKILLed anyway, losing the same work with extra indignity. Write the shutdown test first (send SIGTERM mid-batch, assert zero lost jobs and exit code 0) and the architecture will follow the test, which is the cheapest design review tokio offers.

The same test should also assert what does not happen: no task may swallow the cancellation signal, and no channel may retain jobs silently after close. A shutdown test that checks lost-job count and exit code together catches more async design flaws than any amount of reading, because it forces every component to declare -- under pressure, on a timer -- what it actually promises in-flight work.

How many tasks should one runtime run?

As many as your waiting work requires -- tens of thousands is ordinary -- because tasks are cheap until they compute. The real budget is worker-thread saturation: monitor it, and when compute creeps in, move it to spawn_blocking or a dedicated blocking pool rather than shrinking task counts. Task count limits treat the symptom; saturation metrics treat the cause.

Is async worth it below ~100 concurrent connections?

Usually not: threaded-per-connection code is simpler to debug and fast enough at that scale, and retrofitting to async later is mechanical. Adopt async when concurrency is waiting-dominated and large, or when a dependency (an async-only client library) drags you in anyway -- then adopt it fully, with the lint set and shutdown test from day one.

Why does my async code use more CPU than the threaded version?

Typically poll churn: futures that wake immediately in a loop (busy-wait disguises), excessive tiny tasks spawning per item, or a misused yield_now. tokio-console's poll-count column exposes it in seconds; the fix is batching work per poll and coalescing wakes. Async efficiency is a scheduling discipline, not a free gift from the keyword.
