Third suspect: the machine is lying to you

Turbo boost states, thermal throttling, CPU frequency governors, and unpinned threads on busy cores each swing microbenchmarks by 10–30% -- comfortably larger than most flag effects you are trying to detect. For decisions that matter: pin the governor to performance, pin benchmark threads to isolated cores, run each config interleaved (A/B/A/B) rather than sequentially, and report medians with spreads. The cluster Q&A on benchmarking provers honestly extends this to proof workloads; the principle is identical: a benchmark without a hardware manifest is an anecdote with decimals.

The decision checklist

  • Fingerprint the binary you measured (profile, hash, toolchain).
  • Baseline with criterion before touching flags; save the baseline in CI.
  • Flamegraph first; fix allocator/clone/monomorphization hot spots.
  • Adopt at most one profile flag per change, with its measurement in the commit message.
  • Re-benchmark on pinned cores, interleaved configs, median-of-runs reporting.

Follow the list and "release is slow" stops being a mystery and becomes a queue of measured, reversible decisions -- which is the entire difference between tuning and guessing, in Rust or anywhere else. For the ownership-level performance habits that prevent most hot spots from existing, see the Rust systems programming guide; for binary-size counterparts of these trades, the cluster index routes to the size-reduction Q&A.

Is PGO worth it for my service?

Only if you have a representative workload replay: PGO gains 5–15% on compute-shaped binaries but degrades unpredictably when production traffic diverges from the training profile. For request-driven services, fix hot spots and use thin LTO first; revisit PGO when a stable replay harness exists and the remaining gap justifies its CI complexity.

Why is my release build slower than debug at startup?

Usually static-initialization or first-touch effects: release inlines and reorders aggressively, changing page-fault and I-cache behavior at cold start. Measure startup separately (hyperfine with cold caches) and consider lazy initialization for big tables; a service restarted hourly feels startup latency far more than steady-state throughput.

Should I set opt-level per dependency?

Yes, selectively: hot dependencies (crypto, serialization) at 3 while your workspace stays at 2 is a common win; conversely, dev-profile opt-level 1 for dependencies keeps test suites fast without touching release semantics. Profile overrides are scalpel work -- document each with the benchmark that justified it, or the next maintainer will rightly delete it.
