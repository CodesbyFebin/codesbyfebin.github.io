Measure the anatomy before surgery

Default release binaries are mostly things you did not write: panic-unwind tables, fmt machinery for Display of every error path, monomorphized generics per type instantiation, and dependency features you never enabled deliberately. The anatomy view decides the surgery: a binary whose top entries are core::fmt needs fmt discipline; one dominated by one dependency's unused features needs a Cargo.toml intervention, not a compiler flag. Skip this step and flags become folklore -- the size-world twin of the failure mode the release-optimization guide attacks on the speed side.

Flag layer: the reliable 30-50%

  • strip = true (or objcopy --strip-all): symbols are metadata; gone is 20-40% alone for error-rich binaries.
  • lto = true + codegen-units = 1: cross-crate inlining collapses duplicate monomorphizations.
  • opt-level = "s" (speed-ish) or "z" (size-only): 5-15% further; benchmark runtime after, because "z" occasionally costs double-digit percent.
  • panic = "abort": removes unwind tables; verify no catch_unwind/FFI-unwind reliance first, as the optimization guide's compatibility note details.

Transport layer: compression is a decision, not a trick

If the constraint is transfer rather than resident size (downloads, OTA updates), ship xz/zstd-compressed artifacts or self-extracting wrappers and keep the uncompressed binary for execution; if the constraint is flash or RAM, compression buys nothing post-extraction and costs a decompressor. Firmware OTA pipelines additionally want delta updates (binary diffing between versions), where the size work above pays twice: smaller binaries diff smaller. State which constraint you serve in the release note -- "400 KB gzipped download, 1.1 MB resident" is two numbers with two owners, and conflating them is how teams optimize the wrong byte budget for a quarter.
