Cloudflare Tunnel in twelve commands' spirit

Three hardening notes the quickstarts omit. Bind the origin service to 127.0.0.1 so the tunnel is the only path in (otherwise you have quietly re-opened the port you avoided). End the ingress list with an explicit 404 rule -- cloudflared's implicit default is fine until someone edits the file at 1 a.m. And put the tunnel itself under the monitoring heartbeat from your substrate month: a dead cloudflared process presents as "site down" with every local health check green, which is the most confusing ten minutes in self-hosting.

TLS and caching caveats per route

Tunnels terminate TLS at the edge by default; if your threat model wants end-to-end encryption, run TLS to your origin as well (self-signed is fine inside the tunnel, since the tunnel authenticates the origin by service address) or use Tailscale Funnel, where your node's WireGuard-grade identity covers the leg. Caching follows the same split: edge caches give you global speed but also cache your mistakes -- set explicit Cache-Control on immutable assets and keep HTML short-lived or bypassed, or you will debug a stale deploy for an hour. With the VPS route, all of this is your configuration: DNS-01 wildcards, your caddy or nginx edge, and the mesh as the return path, exactly the shape Decentralized.Host nodes run in production.

When buying a static IP is the right answer

Three situations justify the business-line upgrade or the VPS: you run services that cannot tolerate an intermediary (matrix federation with strict TLS pinning, some VoIP), your audience is local and latency through a far-away edge hurts, or compliance requires you to name your egress addresses. Outside those, the tunnel-or-proxy decision stands -- and note that "static IP" bought at home still leaves your router internet-facing, so it solves addressing, not exposure; the exposure question is answered by the same gates and proxies either way, as the exit-the-cloud guide frames it: own the path you can defend, rent the one you can monitor.

Does a tunnel hurt SEO or cause duplicate-content issues?

No, when the public hostname is canonical: search crawlers see one domain with normal HTTPS, and the tunnel is invisible at the HTTP layer. Problems appear only if you expose the same content on multiple public names (tunnel host plus a DDNS host) -- pick one canonical hostname, 301 the rest, and keep certificates valid; crawlers penalize confusion, not topology.

Can I run the tunnel on the same box as the website?

Yes, and it is the common setup: one systemd service for the site, one for cloudflared, origin on localhost. Isolate them anyway -- separate users, and if possible separate containers -- because a vulnerability in either then compromises one role, not both; the federation's node agent follows the same one-role-per-process rule for exactly this reason.

What breaks first when my ISP changes something?

With tunnels: nothing addressing-related, which is their beauty -- but ISP-level MTU or UDP shaping can degrade the tunnel's own outbound link, presenting as slow-large-page complaints. With DDNS: everything, starting with the client cache TTL you forgot to lower. Monitor tunnel latency percentiles alongside site checks so "ISP changed" shows up as a transport graph, not a mystery.
