ZFS Snapshots and Backups Explained: Send, Receive, Scrub

ZFS snapshots and backups explained: dataset design, snapshot schedules, incremental send and receive, scrubbing and the restore drills that prove the chain works.

Snapshots: the rollback layer

Snapshots cost nothing until data changes (copy-on-write charges only deltas), which makes hourly cadence cheap and surgical recovery trivial: a file deleted at 14:32 lives in the 14:00 snapshot, retrievable by path without restoring anything else. Automate with sanoid-style retention (hourly 24, daily 7, weekly 4, monthly 6 -- tune to your change rate) and treat snapshot lists as capacity data: growth in snapshot-used space is your churn telemetry, and a sudden spike is often the first symptom of ransomware-shaped activity, worth an alert line beside the security stack's own signals.

Send and receive: the replication layer

zfs send -i prev snap | ssh backup zfs recv pool/mirror transfers only deltas, compressed on the wire, with checksums end to end -- replication as mathematics rather than hope. Production rules: send from a held snapshot (bookmark or sanoid-held) so the incremental base cannot expire mid-stream; receive into a readonly=on destination so nobody edits the mirror into divergence; and verify with periodic zfs get -r checksum-guid comparisons or a received-count dashboard. Raw sends carry encryption keys' ciphertext when the source is encrypted (keep keys escrowed per the exit guide), while non-raw sends decrypt at the source -- choose per threat model and write the choice in the runbook, because "is the mirror readable offline?" has different answers per mode and incidents ask at 3 a.m.

Scrubs: auditing silence

Scrubs read every block against its checksums, repairing silent rot from good parity while the pool is healthy -- the feature that separates ZFS from filesystems that discover rot at read-time panic. Monthly cadence for spinning rust (weekly for pools over five years old or with any SMART whispers), after-hours scheduling (scrubs are IO-heavy), and always check the result: a scrub that found and repaired errors is a saved dataset and a disk on probation; a scrub that cannot repair (insufficient redundancy) is an incident in progress. Log scrub outcomes into the monitoring heartbeats from the monitoring guide: "last scrub clean, 0 errors, 4h12m" is a monthly sentence whose absence should page, because silence from the scrub is indistinguishable from a scrub that never ran.

Drills: where snapshots become backups

Keep one more artifact with the drill log: the receive-side feature-flag matrix (pool features enabled per host generation), because cross-version receives fail on feature gaps more often than on capacity, and a one-line table of pool features per machine converts the year's first cross-generation restore from an error-message excavation into a lookup. The table belongs in the same runbook page as the drill timings -- recovery knowledge co-located is recovery knowledge used, a principle this cluster repeats across clusters precisely because every incident review rediscovers it independently.

Pairing with restic: file-level portability

ZFS replication protects pools and datasets as units; restic from a snapshot mount protects files as units -- cross-platform restores, single-file granularity for non-ZFS destinations, and encrypted repositories that travel to object storage per the offsite guide. Snapshot first, restic from the snapshot mount second: consistent source, zero live-file races, and the snapshot becomes the restore point both layers agree on. The pairing costs one extra timer and removes the last argument in the "ZFS means I don't need backups" debate -- a debate that ends, every time, at the first corruption that predates every snapshot you kept.

How much space do snapshots really cost?

Zero at creation, then churn-proportional: a dataset changing 1% daily costs ~1% of dataset size per daily snapshot until retention prunes it. Model it as dataset size times daily churn times retention days, add 10%, and alert at 80% of the modeled envelope -- snapshot-space surprises are almost always churn surprises (a log directory that joined the dataset uninvited), and the model makes the intrusion visible as arithmetic.

Is RAID-Z1 acceptable for backups pools?

For the backup destination pool, yes with scrubs and smartd watching: its failure mode (second disk death during rebuild) is tolerable when the source pool and offsite restic copies still exist -- redundancy requirements scale with how many copies stand behind a pool. For the only pool holding irreplaceable data, RAID-Z2 or mirrors-plus-offsite is the honest minimum; the topology question is really "how many independent copies exist at every moment", and pools are one answer among several, never the whole answer.

Should I encrypt the pool?

Yes for laptops and any pool whose disks might leave your control (RMA, resale, theft); optional for stationary arrays where the threat model says disks die at home. Encryption adds key management to your escrow obligations -- the envelope gains one more tested artifact -- and slightly narrows some dedupe/replication options; decide per pool, write the decision down, and remember that pool encryption protects stolen disks, not running systems, which attackers and warrants both prefer to meet powered on.
