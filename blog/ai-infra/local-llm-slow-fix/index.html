Why Is My Local LLM Slow, and How Do I Fix It?

Why your local LLM is slow and how to fix it: VRAM versus RAM residency, thread counts, KV-cache quantization, context bloat and flags that pinpoint the cause.

Residency: the first number to check

Inference speed is bounded by memory bandwidth times residency fraction: every layer that must page in from disk or host RAM per token multiplies latency. GPU boxes: nvidia-smi shows model bytes versus allocated VRAM -- if weights exceed VRAM, runtimes offload layers to CPU and tokens crawl at DDR speeds while the GPU idles, the signature being high CPU and 5% GPU utilization. CPU boxes: /proc/pressure/memory above ~5 during generation means swap involvement. Fixes in order: smaller quant, shorter context (KV is resident memory too), close competitors, or add the hardware the VRAM math Q&A sizes. Never "fix" residency by raising swap: that converts a slow assistant into a disk-thrashing heater.

Threads: the second number, and the classic overshoot

Context bloat: the slow creep

KV cache grows linearly with context and batch; a "4k default" workflow that became "paste the whole repository" multiplies per-token attention cost and memory pressure simultaneously. Symptoms: first tokens fast, degradation within a session, recovery after /clear. Responses: cap context at what tasks actually use (the histogram signal from the serving guide), quantize KV at q8 where memory binds, and chunk retrieval-style workloads instead of pasting corpora -- a RAG pipeline with 2k retrieved context beats a 16k paste on quality and speed, which is the rare win-win this field offers.

Runtime and hardware mismatch

Thermals: the environmental culprit

Laptops and mini PCs throttle under sustained matmul: clock graphs sagging after 90 seconds while tokens/second sag with them is the signature. Check with sensors or vendor tools during a benchmark run; remedies are physical (airflow, undervolting where supported, a $12 stand) or scheduling (batch jobs at night, interactive use bursty). One measured case from the pilot fleet: a mini PC behind a TV panel lost 38% throughput until relocation -- no config change has ever bought that much, which is why thermals earn the last section and never the last guess.

Why is the first token slow but the rest fast?

Prompt processing (prefill) is compute-bound over the whole context, while generation is bandwidth-bound per token; long prompts therefore front-load seconds of work. Mitigations: prompt caching for repeated prefixes, chunked prefill on vLLM, and not pasting the novel when a paragraph suffices -- prefill cost is the honest price of context, payable once per unique prefix.

Does enabling flash attention change quality?

No: it is an exact algorithmic rearrangement (tiling with online softmax), not an approximation -- identical outputs modulo float associativity noise. It changes memory (KV residency drops) and speed (attention kernels fuse), which is why every serving recipe here turns it on; quantized KV, by contrast, is a real approximation and belongs to the quality conversation instead.

My tokens/s fluctuate wildly between runs. Why?

Usually scheduler noise: background indexing, backup windows, or browser tabs competing for bandwidth and cores. Benchmark with the box quiesced and report medians with spreads; if fluctuation persists on an idle box, suspect thermals or power profiles (laptop on battery caps clocks), both of which show in clock logs during the run -- measure the environment before blaming the model, which is innocent more often than its reputation.
