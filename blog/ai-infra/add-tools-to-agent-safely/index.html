How Do I Add Tools to an AI Agent Safely?

How to add tools to an AI agent safely: capability reviews, schema minimization, sandboxed executors, staged rollouts and the kill switch you test on day one.

The five stages, with their exit criteria

  • 1 Schema review: parameters bounded and typed, no catch-alls, description states side effects truthfully; exit: reviewer signs the schema diff.
  • 2 Classification: run the tool under strace/network watch with adversarial inputs; file by observed behavior into the four-class taxonomy from the safety guide; exit: registry row with class and evidence link.
  • 3 Sandbox trial: two weeks in a session-scoped capability (path-scoped writes, egress-deny), all calls journaled with planner reasons; exit: transcript sample reviewed, no unclassified side effects observed.
  • 4 Promotion review: invocation histogram (used at all?), denial-code spread (schema confusion?), approval-stamp rate (over-gated?); exit: budgets set per class, approval tier confirmed by stamp-rate rule.
  • 5 Registry life: owner named, sunset date defaulting to six months, re-earn on demand; exit criteria for retirement: zero invocations two quarters.

The onboarding traps, observed in registry audits

Documentation optimism: tools described as reads that persist caches or phone home -- stage 2's strace exists precisely because vendors document intent, not behavior. Scope inflation at promotion: a tool trialed path-scoped arriving at registry with global write "for convenience" -- promotion diffs the capability row against trial capability, and the diff needs a signature. Description drift: schema updated, description stale, planner behavior shifts silently -- descriptions are part of the schema diff, enforced by review template. Orphan ownership: tools whose owner left the team keep capabilities by inertia; sunset dates plus quarterly orphan pruning (the config-repo habit, applied to registries) close the loop, per the pruning philosophy in the safety guide's review section.

Metrics that make promotion a decision, not a mood

Four numbers per trial tool: invocation count by session class (is anyone using it, and who), denial rate by code (schema friction), approval-stamp rate (tier calibration), and journal-sample disagreement rate (planner's stated reason versus gate's classification, sampled twenty calls). Publish them in the promotion review doc beside the schema diff; a tool whose numbers nobody reads gets default sunset at six months, which converts registry entropy into scheduled arithmetic -- the same trick the config orphan reviews use, and for the same reason: entropy's only reliable opponent is a calendar with an owner.

Can stages be compressed for urgent tools?

Stages 1-2 never (schema and classification are the load-bearing walls); stage 3 can compress to 72 hours with doubled journal sampling for internal-curated tools, never for open-web-sourced ones. The compression rule is written in the registry policy so urgency debates happen once, at policy time, rather than per tool at 5 p.m. on a deadline day.

How do wrappers fit the staged path?

Wrappers (implementations that make hidden writes explicit, bound unbounded parameters, or add approval prompts) are stage-2 outputs: the wrapper is the tool, the wrapped binary is its dependency, and the registry row cites both. Reviewing wrappers means reviewing the delta they add -- usually under two hundred lines -- which is why wrapper-first onboarding is often faster than arguing with an upstream tool's actual behavior.

What kills a tool fastest post-promotion?

Keep one paragraph per tool beside its registry row -- a biography: why it arrived, what it replaced, what it was expected to change. Biographies make sunset reviews short and re-adoption decisions informed; their absence is felt only during the conversation that needs them most, which is always the one running against an incident timer.
