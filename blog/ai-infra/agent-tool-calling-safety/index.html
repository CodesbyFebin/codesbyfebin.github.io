Schemas as contracts, not suggestions

Capability gates in front of every call

The ordering encodes lessons: capability before scope (a session without the capability never reaches argument parsing), journal before execution (a crash mid-call leaves a record of intent, which forensics needs and apologies cannot supply), and approval as a first-class verdict rather than an exception path bolted on. This is the APG-1 philosophy from the agent security guide applied per tool; the tool-onboarding Q&A covers how tools earn their place in the capability taxonomy in the first place.

Classifying side effects: the write taxonomy

  • Pure reads: cacheable, rate-limited lightly, outputs still untrusted.
  • Local writes: session-scoped paths by default; shared paths require scope tier plus approval.
  • External writes (email, payment, public posts): approval-gated by default with per-session budgets; the "agent emailed the customer" class of incident is entirely this row misfiled as a local write.
  • Irreversible acts (deletes, transfers, publishes): two-person rule or time-delayed execution where stakes warrant; deletion via move-to-trash primitives so undo exists by construction, per the deletion-prevention Q&A.

File the taxonomy in the tool registry beside each schema, and let the gate read it rather than re-dering per call: classification as data, not as code branches, is what keeps the system auditable as tools multiply -- forty tools with per-tool if-statements is forty ways to misfile; forty registry rows with four classes is a reviewable table.

Review loops: where the taxonomy stays honest

Weekly: denial-code histogram (spikes mean schema confusion or capability gaps), approval-hold queue review (holds aging past SLA indicate taxonomy drift, not user patience), and journal sampling of write-class calls reading the planner's stated reason beside the gate's classification -- the sample catches misfiled tools before incidents do. Quarterly: tool sunset review, where unused tools lose capabilities by default and re-earn them on demand; capability sprawl is entropy, and entropy's only opponent is scheduled pruning, the same argument the config-repo orphan reviews make across this entire portfolio. The safety story that survives contact is not a wall of controls but a loop of measurements around five controls, reviewed by named humans on calendars -- everything else is prose.

Should agents be allowed to write their own tools?

Only into a sandboxed executor class with its own gate tier, resource ceilings, and egress-deny, and only with generated-code review before promotion to registered tools -- the promotion path is a human approval by design. Agent-authored tools that skip promotion live and die inside the session sandbox; the boundary between "session scratch" and "registered capability" is the load-bearing wall, and walls need doors with locks, not suggestions.

How do I handle tools that are reads with hidden writes?

Reclassify them: caching layers that persist, analytics calls that phone home, "get" endpoints with rate-state side effects -- audit by running them under strace/network watch at onboarding and file by observed behavior, not by documentation. Tools whose hidden writes cannot be removed get wrapper implementations that make the writes explicit and gated; a wrapper that names the side effect converts a trap into a line item, which is the entire job of this discipline.

Is human approval fatigue a real risk?

Yes, and it is the taxonomy's feedback signal: approval queues with >90% rubber-stamp rates mean the class is over-gated (move down a tier with logging) or under-specified (split the class). Measure stamp-rates per class monthly; the goal is approvals that humans read because they occasionally refuse, and classes where refusal never happens are classes whose gate should be a budget instead -- fatigue is not a human failure, it is a taxonomy error wearing human clothing.
