Where CPU inference actually fits

  • Personal assistants and drafting: 7-12 tok/s reads faster than most people edit; the 8 GB RAM Q&A covers the memory envelope.
  • Gate and classification heads: small models scoring agent actions or routing queries -- milligram workloads where CPU keeps the GPU free for serving.
  • Air-gapped and regulated corners: boxes that may never contain a GPU (policy, power, supply) still deserve assistants; CPU inference is the sovereignty floor of the stack.

Tuning levers, in order of payoff

Threads at physical-core count (hyperthread oversubscription hurts bandwidth-bound loops more than compute-bound ones); flash attention on; KV cache quantized at q8 for contexts over 4k (memory bandwidth is the budget, cache is a spender); prompt processing chunked so first-token latency stays interactive while batch prefetch warms; and model choice by bandwidth division, not by parameter vanity -- a 3B Q8 often beats a 7B Q4 on both quality-per-byte and tokens-per-second for narrow tasks, a trade the quantization comparison prices per task family. Measure after each lever with a fixed 200-token generation harness; CPU inference tuning without a harness is weather forecasting with a wet finger.

The honest ceiling, and the GPU handshake

Three workloads should leave CPU immediately: multi-user interactive serving (concurrency divides your already-modest bandwidth), long-context generation beyond 16k (KV traffic joins weight traffic in the same narrow pipe), and frontier-quality demands (the models that satisfy them do not fit the bandwidth budget at any quantization that preserves them). The mature architecture therefore treats CPU and GPU as one fleet: CPU boxes absorb batch, embed, and gate workloads plus overflow drafting; GPU boxes hold interactive sessions; the gateway routes by model class and quota. That handshake -- cheap silicon doing what cheap silicon is good at, expensive silicon rationed to what only it can do -- is the same shape as the federation's node classes in decentralized.hosting, because capacity economics does not care whether the resource is watts, watts, or watts.

Is CPU inference worth it versus a $200 used GPU?

Usually yes for the first step: CPU needs no drivers, no VRAM envelope, no power draw beyond the box you own, and fails boringly. The used GPU upgrades tokens-per-watt dramatically but adds the VRAM mathematics, thermals, and driver maintenance from the VRAM guide. Sequence: prove the workload on CPU, measure its value, then let the measurement buy the GPU -- purchases after measurements age better than purchases before them, in inference as in every other line of the cost sheet.

When someone asks why the household keeps a box that "only" manages seven tokens a second, point at that chart and at the invoice it replaced: seven tokens a second, multiplied by every night of the year, is a private library of summaries, embeddings, and drafts that never left the building -- and speed was never the property anyone was actually buying. The property was custody, and custody, measured in watts and journal lines, is the one benchmark no vendor chart can quote back at you.
