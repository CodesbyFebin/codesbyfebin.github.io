The system+runtime row is the forgotten term: OS, shell, editor, and the runtime's own arenas consume 1.5-2.5 GB on a lived-in machine before the model loads. Measure your idle baseline (free -h after login, not at boot) and subtract it from 8 GB before believing any model-size chart, including this one -- the table's spare column is what separates "loads" from "loads and stays responsive while your editor is open".

Settings that keep it usable

Thread count surprises people: more threads than physical cores adds synchronization overhead and memory pressure without tokens, so start at physical-core count and tune down if the box feels sticky. KV quantization (-ctk/-ctv q8_0) halves the cache's RAM at quality cost measurable only with calipers at 4k context. --mlock pins weights so the OS cannot page them out under editor pressure -- the single most effective flag for "it was fast yesterday" complaints on shared boxes.

The swap trap and how to see it coming

When weights plus KV plus lived-in OS exceed RAM, Linux swaps cold pages and generation becomes seek-bound: tokens arrive in bursts separated by disk stalls, fans scream, and the model "feels broken". Detect with /proc/pressure/memory (some-avg10 above ~5 during generation) or vmstat's si/so columns moving at all. Responses, in order: drop context length first (KV shrinks linearly), then quantization tier, then close apps, then -- last -- add swap as a crash absorber rather than a capacity plan. The cluster's slow-LLM diagnosis Q&A walks the same signals from the other direction, and the serving guide shows what changes when this box graduates to a GPU.
