Why MCP exists: the N×M integration problem

Before MCP, every agent framework that wanted every tool needed a bespoke integration: N frameworks times M tools, each with its own auth, serialization, and error semantics -- the classic N×M tarpit that plug-and-play standards exist to kill. MCP replaces it with N+M: servers speak one protocol, hosts speak one protocol, and the contract between them is a typed tool schema plus a negotiated capability set. The practical consequence for you as a builder: implement the protocol once and your tool becomes reachable from any compliant host, without shipping a framework SDK.

Architecture: hosts, clients, servers, tools

Three roles, one session. The host is the user-facing application (an IDE, an assistant, an automation runner). The client is the host-side connection object that negotiates and routes calls. The server is your process: it declares tools, resources, and prompts, and executes requests inside whatever boundary you choose. Sessions are stateful and begin with an initialize handshake in which both sides declare protocol version and capabilities; anything not declared is unavailable, which is your first -- and cheapest -- safety gate.

  • Tools: model-invoked functions with JSON Schema inputs/outputs. The model sees name, description, schema -- nothing else.
  • Resources: host-readable data (files, records) addressed by URI, fetched on demand.
  • Prompts: user-invoked templates; the least dangerous primitive and the most underused.

Transports: stdio for local, streamable HTTP for remote

Stdio transport runs the server as a child process with JSON-RPC over stdin/stdout: zero network surface, perfect for local tools, and the default you should teach first. Streamable HTTP serves the same session semantics over POST/SSE for remote or multi-tenant servers, and immediately inherits web threats: auth, replay, tenant isolation. Rule of thumb: stdio unless you can name the network threat that justifies HTTP -- and if you can, budget for its mitigations in the same sprint.

Two transport details bite implementers late, so meet them early. First, stdio servers must keep stdout pristine: one stray console.log or library banner corrupts the JSON-RPC stream for the entire session, and the failure presents as inexplicable parse errors on the host side -- route all human logging to stderr from line one, and add a test that asserts stdout contains only newline-delimited JSON during a scripted session. Second, HTTP sessions are server state: a restart orphans in-flight sessions, so design idempotent tool calls (content-addressed inputs, deterministic outputs) and return typed "session lost" errors that hosts can retry from scratch. Neither detail is glamorous; both separate servers that survive operations from servers that survive demos, and the difference shows up in exactly the places -- logs and restarts -- where unglamorous failures live. Budget an afternoon for each when you first adopt a transport; both afternoons repay themselves at the first 3 a.m. restart, which is the only hour that ever tests them. Write the two tests down in the repository README beside the transport choice, so the next maintainer inherits the reasoning and not just the configuration, six months after the incident that taught it has faded from everyone's memory.

Step 2 -- Capability negotiation and lifecycle discipline

During initialize, declare exactly what the server offers (tools, maybe resources) and read what the host declares. Then enforce lifecycle rules that most tutorials skip: tools list changes require a tools/list_changed notification or the host caches stale capabilities; cancelled requests (notifications/cancelled) must abort in-flight work promptly, or a timed-out agent leaves orphan provers burning CPU; and every error returns structured isError content, because a stack trace dumped as "success text" becomes part of the model's context -- and context is attack surface.

Step 4 -- Policy gates: deny by default, journal everything

Two subtleties separate gates that hold from gates that theater. Evaluation order must be deterministic and documented: most-specific-scope first, ties to deny, and the ordering itself covered by tests -- a policy engine whose precedence is emergent is a random-number generator with a config syntax. Denials must be informative to the model but minimal to the adversary: return the capability name and the policy tier that refused, never the full policy document; agents plan better with reasons, and attackers learn nothing from them. Both properties are normative in APG-1 precisely because they were learned the expensive way, in reviews where a verbose deny leaked an entire tenant policy to a prompt-injected session.

Step 5 -- Testing the server like infrastructure, not like a demo

Four test classes cover the failure surface: schema fuzz (oversized, malformed, unicode-hostile inputs must produce typed errors, never crashes); lifecycle (cancel mid-proof, close mid-batch, reconnect with stale capability cache); policy (every APG-1 case asserts verdict and journal line); conformance (protocol version handshake against two different host SDKs, so you notice breaking changes when CI does, not when a user does). A server that passes these four is an infrastructure component; a server that only passes happy-path demos is an incident with a README.

Field notes: the three failures I see in review

First, description drift: tool descriptions that promise more than the schema allows, so models hallucinate parameters the validator then rejects -- keep description and schema in one code block, reviewed together. Second, silent truncation: servers that clip oversized input instead of erroring, producing proofs of programs the user never submitted -- the worst failure class in this entire space, and a one-line guard. Third, credential leakage through resources: exposing a resource URI space that includes config files holding the server's own secrets -- enumerate resources explicitly; never glob a home directory. Fourth, timeout asymmetry: hosts that timeout calls at five seconds while provers run for twenty, then retry -- tripling load precisely when the system is already slow; publish your latency contract in the tool description and let hosts negotiate ceilings instead of guessing them. Each of these has a named test in the suite above; adopt the tests even if you adopt nothing else.

Observability: the journal is the product

Tie the journal to your alerts with three rules only: deny-rate spikes (policy drift or a confused agent), latency p99 breaches (executor ceilings about to bite), and any needs_approval older than its SLA (a human forgot a queue exists). Everything else is dashboard decoration. This mirrors the federation alerting philosophy in operations notes: few alerts, each actionable, each with a named owner.

Remote and multi-tenant deployments: what changes

The moment a server leaves stdio and serves streamable HTTP to multiple tenants, four new obligations arrive. Authentication before protocol: mTLS or bearer tokens with per-tenant key rotation, because an MCP session inherits everything its transport trusts. Isolation: per-tenant executor pools and tmpdir namespaces, so one tenant's runaway proof cannot starve or read another's; quota counters sit in front of the gate, not behind it. Replay defense: nonces or short-lived session tokens on mutating tools, since a captured tools/call is otherwise a valid request forever. Egress policy per tenant: the default stays net:deny, and exceptions are tenant-scoped policy documents reviewed like code. None of this is MCP-specific; it is web security re-asserting itself on a new wire format -- which is precisely why the protocol's typed surfaces make those obligations easier to enforce here than in the bespoke integrations MCP replaced.

Where to go next

You now have a server shape that survives contact with real agents: bounded schemas, negotiated capabilities, sandboxed execution, policy gates, and four test classes. Natural continuations: the companion guide on building the executor internals, the plain-terms overview what MCP is for when you need to explain it to a manager, and the gate-hardening Q&A on stopping agents from deleting files. For the proof tools themselves, the reference implementation is mcp-prove-server, and the normative policy grammar lives in APG-1. Keep the alert set ascetic -- deny-rate spikes, latency p99 breaches, stale approvals, and the two heartbeat absences -- because alert fatigue is the tax every monitored system pays whether or not it budgets for it, and a gate nobody trusts is a gate nobody fixes.

Should my MCP server expose resources or only tools?

Start with tools only. Resources are ideal for stable, read-only data (records, docs), but every URI space you expose is a surface to enumerate and policy-check. Add resources when a host genuinely needs pull-based reads, and enumerate them explicitly -- never expose a directory-shaped URI space that includes your own configuration.

Is stdio transport safe if the host is compromised?

No transport saves you from a compromised host: the host spawns your process and sees everything on the wire. Stdio minimizes the remote surface (no listener, no auth stack to get wrong), but your executor ceilings and policy gates are the real defense -- they limit damage per session regardless of who is holding the client end.

How do I version tools without breaking connected hosts?

Treat tool schemas as public APIs: additive changes (new optional fields) ship under the same name; breaking changes get a new tool name with a deprecation period announced via list_changed notifications. Pin protocol version at initialize and reject unknown majors loudly -- silent incompatibility is how agents end up calling tools whose semantics changed under them.
