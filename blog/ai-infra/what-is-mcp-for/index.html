What Is MCP For, in Plain Terms?

What MCP is for in plain terms: a standard plug for tools and context so agents can call your systems safely — with one worked example from schema to sandbox.

The problem it solves, in one diagram of words

Without a standard, three agent frameworks wanting four tools need twelve bespoke integrations, each with its own auth, serialization, error semantics, and security review. With MCP, the same world needs three plus four: every server implements the protocol once, every host speaks it once, and the contract between them is a JSON Schema plus a capability handshake. The integrations stop being projects and become configuration -- which is exactly what happened to printers, storage, and charging before it.

What MCP is not

  • Not a model API. It carries tool calls and data, not tokens; your LLM endpoint stays separate.
  • Not a sandbox. The protocol validates shapes, not consequences -- execution boundaries are still your job (child processes, ceilings, policy gates).

That last distinction matters operationally: a server honestly declaring an exec tool is protocol-correct, and pointing an agent at it without a deny-by-default gate is still an incident waiting for a prompt. The gate layer -- APG-1 style policies, journals, approvals -- sits between negotiation and execution, and it is where the MCP tutorial spends most of its length.

A sixty-second worked example

Notice what is absent: no shell, no file paths, no credentials in arguments. The server's entire surface to the model is a name, a description, and a bounded schema -- which is precisely why the ecosystem can afford to let strangers publish servers while still sleeping at night, provided hosts enforce policy at the gate.

When you should (and shouldn't) reach for it

Use MCP when multiple hosts or agents need the same tools, when you want policy enforcement at a single choke point, or when you are tired of maintaining SDK glue. Skip it for a one-script automation (call the function directly -- indirection is a cost), and skip it when your "tool" is really arbitrary code execution: that is a sandbox product, not a protocol server. For building your first server end to end, the companion guide how to build an MCP server walks the four components; for keeping agents harmless once connected, see stopping agents from deleting files, and the reference implementation with policy gates lives at mcp-prove-server.

Does MCP work with local models, or only cloud APIs?

Entirely with local models: MCP sits between the agent loop and your tools, so the model's location is irrelevant. Local setups actually benefit most, because the gate layer gives you an enforcement point that cloud vendors otherwise provide -- and with local inference plus MCP gates, no part of the loop leaves your machine by default.

Is MCP secure enough to expose to the internet?

The protocol is not the security boundary; your transport auth, tenant isolation, and policy gates are. Stdio servers have no network surface at all. Streamable-HTTP servers must carry real authentication and per-tenant sessions before anything else -- treat an unauthenticated public MCP endpoint as an unauthenticated shell endpoint, because with a permissive server, it is.

How is MCP different from function calling in model APIs?

Function calling is a model-vendor feature for passing structured arguments; MCP is a cross-vendor session protocol with discovery, negotiation, cancellation, and resources. They compose: a host may translate MCP tools into vendor function schemas per model. MCP's added value is portability and the single enforcement choke point -- vendor function calling gives you neither across vendors.
