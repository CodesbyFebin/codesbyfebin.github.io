Rows are cycles, columns are wires

Think of the trace as a spreadsheet the machine fills while running: row t records everything true at cycle t. Registers become sixteen columns; a jump sets a flag column; a memory touch writes address and value into channel columns. The AIR then expresses semantics as relations between row t and row t+1 -- "if the add flag is set, next R3 equals R1 plus R2" -- which is why trace columns are often called wires: they carry the values constraints consume. A clean mental test for trace quality: can you point at the column that would betray each bug class? If a misbehaving instruction leaves every column honest-looking, your trace is under-specified, and no proof system rescues an unfaithful witness.

Memory channels: making RAM provable

Registers are easy (fixed columns); RAM is the interesting part, since addresses appear dynamically. The standard trick is a memory channel: columns for address and value plus a permutation argument that sorts and matches every read against its write, so consistency ("reads return the last write") is enforced without simulating memory in constraints. Append-only logging with zero-fill for reads-before-writes keeps the argument simple, at the price of two or four columns -- the exact design in rust-stark-zkvm, where streaming friendliness of the log outweighed the width cost. If your trace has no memory channel and your machine has memory, ask what is enforcing consistency; silence there is not efficiency, it is an unproven assumption.

Does trace width affect verification cost?

Barely: verification cost tracks query count, field size, and FRI depth -- functions of security parameters and trace length, not width. Width is a prover-side bill, which is why prover-optimized layouts never need to negotiate with verifier constraints; keep that asymmetry in mind when someone proposes widening "just a little" for debugging columns -- ship them behind a feature flag instead.
