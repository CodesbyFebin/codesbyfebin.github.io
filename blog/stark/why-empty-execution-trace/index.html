Why Is My Execution Trace Empty or Shorter Than Expected?

Why your execution trace is empty or too short: halt-path bugs, input loading mistakes, cycle accounting errors and the assertions that catch each at build time.

Cause 1: the halt that arrived early

Cause 2: pc escapes the program

Misencoded jump immediates (absolute where relative was assumed, or sign-extension lost) send pc outside the code vector. In debug builds this panics on index (loud, good); in release-with-wrap it silently indexes a padded or repeated region and halts early on garbage (quiet, bad). The fix pair: bounds-check pc in the step function with a named error (never wrap), and add a trace-shape test asserting final pc equals the halt instruction's index for canonical programs. The constraint-debug Q&A's first-row localization works unchanged here -- an escaped pc shows as a deviation row whose frame is all padding, the signature of a machine that left its own program.

Cause 3: the step that stepped on nothing

Rust-specific and humbling: a step function taking state by value in a loop that reassigns a copy, or mutating through a clone obtained for "logging", produces traces where registers never change and loops exit on stale counters -- short traces with plausible-looking rows. Detection: differential execution against an independent interpreter (the trace article's two-witness method); where columns diverge at row one, your mutation path is the bug. The ownership redraw habit from the systems guide prevents the class: state lives in one owner, steps take &mut, and "logging copies" are forbidden in executor code by review rule.

Guards that make the class unrepresentable

  • Cycle-budget floor: assert row count ≥ 1 and ≤ budget; empty traces fail loudly at execution, not at prove time.
  • Halt uniqueness: exactly one row with halt=1, and it is last -- one assertion kills causes 1 and 2's quiet variants.
  • Canonical ladder tests: five tiny programs (straight-line, loop, jump-taken, memory-touch, halt-immediate) with expected exact row counts; every executor change runs the ladder first.
  • Trace-shape snapshots: golden-file the column statistics (toggle rates) for the ladder; shape regressions fail merges even when counts pass.
Can padding make a short trace look normal?

Yes, dangerously: padding fills to power-of-two, so a 3-cycle trace presents as 4,096 rows of idle and proofs "succeed" attesting almost nothing. This is why halt-uniqueness and row-count-floor assertions matter more than length checks -- length lies by design (padding), while halt position tells the truth about where your machine actually stopped thinking.

My trace is correct but shorter than my cycle estimate -- bug?

Not necessarily: estimates often count instructions, while cycles count steps (taken jumps cost one, multi-cycle ops cost their declared count). Reconcile against the ISA's cycle semantics table in the ZKVM-ISA spec; a trace shorter than instruction count, however, is always a bug, since every instruction costs at least one cycle by construction.

Should the executor or the AIR catch these failures?

The executor, always: trace-layer failures are specification failures (wrong machine), while AIR failures are legality failures (right machine, illegal step). Catching machine bugs at the AIR costs you prover runs and ambiguous deviations; catching them at execution costs microseconds and names the cycle. The boundary is the same as the one between "the program is wrong" and "the proof is wrong" -- and every hour spent enforcing it early saves three during incident review.
