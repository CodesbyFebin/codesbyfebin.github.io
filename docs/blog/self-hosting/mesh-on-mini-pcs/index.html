Can I Run a Federation Mesh on Mini PCs?

Can you run a federation mesh on mini PCs? Measured quorum performance, power costs, storage heartbeat loads and the node counts where ARM boards struggle.

What the pilot actually measured

Two mini-PC nodes (8 GB, NVMe 512 GB, 10-12 W idle under node agent plus monitoring) joined a federation with VPS and bare-metal peers: heartbeat CPU under 2%, Merkle storage-proof generation for 400 GB datasets completed inside window at ~4% duty cycle, and quorum votes never approached latency budgets. The binding constraints appeared elsewhere: a 2 TB heartbeat dataset tripled proof-window CPU (still fine, but visible), and one node in a closed media cabinet throttled under summer ambient and missed two windows -- a placement failure, not a compute failure, now on the commissioning checklist per the production checklist's thermal point.

Sizing rules that transferred

  • RAM 8 GB floor, 16 GB comfort: node agent plus containers plus monitoring headroom; below 8 GB the monitoring stack starves first, per the RAM Q&A.
  • NVMe for heartbeat datasets: storage-proof generation is random-read shaped; spinning disks extend windows until they miss them.
  • Watt budget per role: quorum node 10-15 W, edge-cache node 8-12 W, proving worker -- not a mini PC job; route proof batches to metal or queue them overnight.
  • Network first-class: wired where possible; the pilot's one Wi-Fi node produced more heartbeat jitter than every other variable combined.

Where small boards genuinely struggle

Three workloads outgrew mini-PC class in pilot logs: multi-TB storage heartbeats (window CPU scales with dataset; above ~4 TB move proofs to a co-located bigger node or shard the dataset), concurrent transcoding for media federations (thermals, not cores, decide), and anything GPU-shaped. Also honest: ARM mini boards (Pi-class) ran node agents fine but stumbled on some container image availability and NVMe boot quirks; x86 mini PCs avoided both, which is why the pilot standardized on them -- boring availability beats theoretical watt savings when the node holds quorum weight, a trade the federation operations notes price explicitly in admission criteria.

Commissioning checklist for a mesh mini node

  1. Placement audit: airflow in and out, ambient logged one week before admission.
  2. UPS or at minimum clean-power strip with surge sacrifice logged; probation nodes on UPS first.
  3. Wired network, static mesh address, hostname in mesh DNS per the mesh tutorial.
  4. Heartbeat dataset sized and benchmarked: proof window under 20% duty at commissioning, alert at 60%.
  5. Probation period served at partial traffic with window metrics reviewed before full weight -- the federation's admission rite, unchanged by hardware class.
Do minis survive the monsoon-season power chaos?

With UPS, yes -- the pilot's Kerala node rode eleven outages in one season with zero missed windows beyond UPS-runtime exceedances twice, both during multi-hour events where the clean-stop policy engaged exactly as the power Q&A choreographs. Without UPS, the same node would have missed all eleven; the hardware was never the variable, which is the sentence every homelab power conversation eventually arrives at.

Worth running proof workers on minis overnight?

For small traces (CI-gate scale, ≤2^18 cycles), yes: overnight queues absorb them at watt-costs that make the economics charming. For million-cycle workloads, the memory ceiling from the cycle-ceiling Q&A bites before morning; route those to metal and let minis do what minis do best -- be everywhere, always on, quietly voting.
