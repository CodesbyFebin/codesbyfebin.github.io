Homelab to Production: The 41-Point Checklist I Actually Use

A homelab-to-production checklist of 41 points: power, networking, observability, change management, backups, security baselines and the docs future-you needs.

Physical and power (points 1-6)

  • 1. UPS on every stateful box, sized to measured shutdown sequence plus 50% margin.
  • 2. AC-restore plus boot-verification tested by pulling plugs quarterly, per the power-loss Q&A.
  • 3. Thermals logged: intake/exhaust deltas and CPU package temps trended; dust on a calendar, not on a smell.
  • 4. Disk provenance recorded: purchase date, workload rating, SMART baseline at commissioning.
  • 5. Label everything that unplugs: cables, PSUs, UPS outlets -- the 2 a.m. taxonomy problem is real.
  • 6. Spare shelf: one PSU, one boot disk, one data disk class, imaged and ready.

Network and exposure (points 7-12)

  • 7. Management plane (router UI, IPMI, hypervisor) unreachable from WAN -- verified by external scan.
  • 8. Mesh or VPN as the default path in; port forwards are named, dated, reviewed entries.
  • 9. DNS under your control with DNSSEC where the provider allows; wildcard strategy documented per the DNS-01 guide.
  • 10. Edge default-deny ingress; every public hostname has an owner and a purpose line in the edge changelog.
  • 11. Egress filtered per host where feasible; inference and backup hosts egress-deny by default.
  • 12. Network diagram versioned in the config repo, updated in the same commit as topology changes.

Configuration and change (points 13-20)

  • 13. Everything in Git: compose/Nix/Ansible, edge configs, timer units, dashboards-as-code.
  • 14. No edits on boxes: a config change is a commit, a review (even self-review counts written), a deploy.
  • 15. Secrets in a manager, referenced not embedded; rotation dates in the calendar with owners.
  • 16. Deploy path is one command with a dry-run mode and a printed rollback command.
  • 17. Rollbacks rehearsed: each service's rollback executed at least once per year, logged.
  • 18. Version pinning with an update policy: security jumps queue, feature updates ride the monthly window.
  • 19. Boot-from-zero proven: one bare-metal rebuild drill per year from repo plus secrets envelope.
  • 20. Machine-readable inventory: hosts, services, owners, dependencies -- the graph incidents navigate.

Observability and backups (points 21-30)

  • 21-25. The five dashboards and four alerts from the monitoring guide: pressure, disks, heartbeats, network, power; backup/cert/tunnel/ups alerts owned by name.
  • 26. Backup chain: restic offsite plus ZFS receive where pools exist, per the ZFS guide.
  • 27. Weekly automated partial restores with canary diff; quarterly full drills timed and logged.
  • 28. Escrow envelope: secrets, restore procedures, emergency contacts; tested annually with the drills.
  • 29. Log shipping off-box: journals or Loki to the backup target; local logs die with local disks.
  • 30. Uptime probes from outside the LAN see what users see, not what your LAN believes.

Security, docs, and the human layer (points 31-41)

  • 31-34. Security baseline: SSH keys only, unattended security upgrades, WebAuthn on every admin surface, exposure checklist re-run per new service per the exposure guide.
  • 35-37. Docs: one-page runbook per service (restart, rollback, escalate), this checklist printed beside the rack, and a changelog culture where every incident ends with a diff somewhere.
  • 38-39. Humans: named owner per service (households included), successor clause and bus-factor review quarterly per the mentorship philosophy.
  • 40. Maintenance window on the calendar with a standing agenda: updates, drill rotation, orphan pruning, labor-line row.
  • 41. The meta-point: review this checklist quarterly and delete what no longer applies -- a checklist that only grows becomes wallpaper, and wallpaper protects nothing.

Adoption advice from four years: score yourself honestly, fix the power and backup clusters first (points 1-6, 26-29) because they decide whether failures are events or losses, then work outward. Teams and households that reach 35 of 41 with owners named run quieter than most startups' production; the remaining six are usually the honest exceptions -- documented, dated, and accepted, which is what "production" finally means: not perfection, but known shape.

Which points can a solo homelabber skip honestly?

None skipped, several scaled: succession (38-39) becomes the escrow envelope plus one informed relative; review cadences become quarterly instead of monthly; "teams" becomes you-with-a-calendar. The points that must never scale to zero are 1-2 (power), 13-14 (config in Git, no live edits), 27 (restore drills), and 41 (review the list) -- those four are the difference between a homelab and a liability.

How do I introduce this to a resistant team or household?

Start with the drill that scares everyone once (restore one important dataset together), then let the checklist grow from the post-drill conversation -- adopted points stick because they answer a felt wound. Checklist imposition without a shared incident memory produces compliance theater; shared scars produce owners, and owners are the only infrastructure that maintains infrastructure.

Is this checklist compatible with managed cloud hybrids?

Entirely: points map onto cloud controls (UPS becomes AZ design, escrow becomes key management policy, drills become game days). Hybrids should run the checklist per environment with a column noting where the provider owns a point -- the column's emptiness or fullness is your sovereignty metric, and reviewing it annually is exactly the exception-review habit the exit guide prescribes for stayed workloads.
