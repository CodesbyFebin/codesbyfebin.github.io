PostgreSQL persistence and local preview boundaries

Understand the supplied Neon and PGLite integration, server-only access, migrations, ownership checks, and deployment persistence.

Choose persistence deliberately

The supplied template offers PostgreSQL-backed persistence with a local embedded fallback. A browser-local preference does not need a shared database. Records that must survive across devices or be shared between users do. Make that requirement explicit before introducing migrations and operational dependencies.

Preview is a different environment

The local PGLite fallback can make a preview work without a provisioned remote database. That is useful for development, but successful preview writes do not establish deployed durability. Record which database source the application is using, and confirm that a production restart preserves a synthetic record.

Keep access on the server

The supplied database helper belongs in server functions or server loaders. A database connection string is a server credential and should not appear in client bundles or API responses. Put schema changes in migrations with a deliberate order, and keep query values parameterized rather than building SQL by concatenating user input.

Ownership is part of the query

For user-owned records, obtain the caller identity from the session and enforce it in reads and writes. A correctly parameterized query can still disclose another user's data when the ownership condition is absent. Test that a guessed resource identifier cannot cross the tenant boundary.

Plan failure and recovery

Connection availability, migration compatibility, and backup restoration are separate concerns. An application that can write one row may still fail during a dependency outage or upgrade. Test an unavailable database and preserve an explicit error state. Restore a backup into an isolated instance before describing the installation as recoverable.

Validate the deployed mode

Use synthetic data to test write, read, restart, and read again. Inspect the documented provisioning switch in the actual platform instead of assuming the presence of migration files selects the correct backend. The static portfolio includes no database; this guide is an adaptation of the supplied platform documentation.

Source and scope
