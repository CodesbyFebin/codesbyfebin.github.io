Self-Hosted Vector Database Comparison: Qdrant vs Chroma vs pgvector

Self-hosted vector database comparison: Qdrant vs Chroma vs pgvector on recall, memory, ops burden and backup story — with the small-dataset verdict teams need.

Recall first: the number that is not a differentiator

The three operational stories

  • Chroma: embedded or client-server; the embedded mode is prototyping gold (vectors in your process, zero services) and the trap: moving to server mode later changes consistency and persistence semantics you assumed. Use it to prove retrieval value in a weekend, graduate deliberately.
  • pgvector: vectors as a column beside your relational rows; HNSW indexes in recent versions make million-row workloads practical; joins and filters are plain SQL, which your team already reviews competently. Ceiling: very large corpora and high QPS push you out, but "very large" is farther than most estates ever walk.

Memory and persistence behavior under stress

The stress tests that decide long-term happiness: kill -9 during indexing (Qdrant's WAL replays cleanly; embedded Chroma's durability depends on your embedding discipline; pgvector inherits Postgres crash recovery -- the strongest story of the three, because it is Postgres's story). RAM exhaustion (Qdrant's quantization and on-disk modes degrade gracefully; pgvector shares the database's memory pool, so budget shared_buffers with vectors inside the same envelope per the RAM sizing guide; embedded Chroma competes with your application for the same heap). Backup integration (pgvector dumps with the database -- one tool, one drill; Qdrant snapshots need their own row in the backup chain; embedded stores hide inside app directories until someone audits them, which is how they get missed by restic include-lists, the silent-exclusion class from the restic guide).

Choosing in one paragraph, with the graduation path

Prototype in Chroma embedded because weekends are short; if retrieval earns production space, choose by data gravity: vectors beside relational truth that must transact together go to pgvector (one backup, one drill, one story); vectors as their own corpus with heavy filtering and quantization needs go to Qdrant (one service, one snapshot hook). Both graduations keep the retrieval layer behind your gateway's interface so the engine swap is a config commit, not a client migration -- the alias-table trick from the gateway guide applied to search. And whichever you run, pin embedding model versions in the same manifest as the index: embeddings are the schema of vector land, and an unversioned embedding model is a schema migration nobody scheduled, discovered by recall drift that no dashboard can attribute.

How large before leaving a single box?

Single-box comfortable ceiling: ~5M int8-quantized 768-dim vectors with HNSW in 32 GB RAM including headroom, at interactive latencies. Beyond that, shard by tenant or time (both engines support it) before buying clustering complexity -- sharding on a dimension you already filter by is free partitioning, and free partitioning beats purchased orchestration every time the filter exists.

Is disk-based (on-disk HNSW) worth it?

For cold corpora queried occasionally (archives, compliance search), emphatically yes: NVMe-backed indexes cut RAM 5-10x at 2-4x latency, a trade archives happily make. For interactive RAG, keep hot collections resident and archive cold ones to on-disk or to restic shelves with a rehydrate runbook -- tiering vectors like tiering storage is the same discipline at a new altitude, and the runbook row is what makes the cold tier honest.

Whichever engine you choose, commission it with the four artifacts every other service in this cluster receives: a runbook page (reindex procedure, restore-from-snapshot steps, embedding-version migration), a heartbeat in monitoring (index lag, query p95, RAM headroom), a backup row naming exactly what is backed up (snapshots or dumps plus the embedding manifest -- backing up vectors without their embedding pin is backing up ciphertext without its key), and a sunset review date for the day corpus growth crosses the single-box ceiling. Engines differ in features; estates differ in whether those four rows exist, and it is the rows, not the engine, that decide whether year two of your retrieval stack reads as operations or as archaeology. Pin the embedding model hash in the same manifest as the index, journal every reindex with its before/after recall on the eval set, and let the manifest plus journal answer the only two questions an audit will ever ask about your retrieval stack: which vectors are these, and what changed them last.

When the sunset date arrives and the corpus has outgrown the box, graduation is a config commit plus a reindex window, not a rescue: engines behind one interface, embeddings pinned, backups drilled -- the three properties that turn any future migration into an event with a schedule instead of an incident with a story. Schedules, unlike stories, can be slept through; and a retrieval stack that can migrate in its sleep is the retrieval stack its owners recommend to friends, which is the only endorsement this cluster has ever accepted as evidence.
