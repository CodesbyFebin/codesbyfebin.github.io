How Do I Stop an AI Agent From Deleting Files?

How to stop an AI agent deleting files: read-only mounts, path-scoped policies, confirmation gates, snapshot-before-run workflows and journal alerts on deny.

Why behavior tricks fail and capability gates don't

Prompt-level instructions ("never delete files") are suggestions to a stochastic system; prompt injection, ambiguous plans, and plain misjudgment all bypass them routinely. Capability gates are different in kind: the agent's tool call is checked against policy before execution, in code, with deny-by-default semantics. An agent told to "clean up the workspace" against a read-only mount produces a logged deny and an adapted plan -- the failure is absorbed by architecture, not by the model's mood that day. This is the core argument of the APG-1 specification: make the safe path the only path.

The four-layer stack, in order of importance

  1. Read-only by default. The agent's filesystem tool sees a read-only view; writes happen only through an explicit fs_write tool whose policy grants specific path prefixes. Most sessions never need it.
  2. Path-scoped grants. fs:~/proj/src:rw beats "filesystem access" the way least privilege beats root: the blast radius of a bad decision is one directory, and the journal shows every grant exercised.
  3. Confirmation gates for destructive verbs. rm, recursive moves, force-push, schema drops: policy returns needs_approval, a human (or a stricter policy tier) decides, and the decision is journaled with prompt-hash.
  4. Snapshots before runs. A git commit, ZFS snapshot, or restic backup taken automatically at session start converts "deleted" into "reverted in 40 seconds" -- the difference between an anecdote and an incident.

Proving the gates: deletion attempts as test cases

When something still gets deleted

Assume it eventually will -- through a tool you forgot to gate, or a grant scoped one directory too wide. The response plan is what makes that survivable: snapshot-first means restore is routine; the journal means root-cause is a query ("which grant allowed this path?"); and the postmortem ends with a policy diff, not a promise. Teams that treat deletion incidents as policy bugs converge quickly; teams that treat them as model misbehavior keep relitigating the same prompt forever.

Is a confirmation prompt for every write too annoying in practice?

Yes -- which is why confirmations attach to destructive verbs and out-of-scope paths, not to writes generally. Scoped rw grants inside a project feel invisible in daily use; the friction concentrates exactly where the risk does. If users start rubber-stamping approvals, tighten scopes or add an auto-allow tier for file types; never remove the journal.

Does read-only mounting break build tools that need caches?

Often -- so grant caches explicitly as their own prefix (fs_write:~/.cache/build:rw) rather than widening the project grant. Caches are precisely the directory you can afford to lose, which makes them the perfect pressure valve: the agent gets writability where destruction is cheap, and your source tree stays a fortress.

Can the agent delete files via exec instead of fs tools?

Only if exec is granted -- and in the policy above, it is denied except one pinned command. That is the point of evaluating every capability through the same gate: agents do not care which door they use, so neither can you. Audit your tool list quarterly for accidental shells: interpreters, package runners, and editors are all exec in disguise.
