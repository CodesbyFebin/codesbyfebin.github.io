How Should I Cache LLM Responses Without Stale Answers?

How to cache LLM responses without serving stale answers: semantic keys, TTLs by content type, invalidation hooks and the audit trail that makes caching safe.

The three layers, and what each buys

  • Exact-match: key = sha256(model-id + version + serialized prompt + sampling params + system text); hits are free latency and free watts; TTLs by volatility class (facts: hours; drafts: minutes; codegen: hours with invalidation on dependency hashes where available).
  • Prefix/prompt-cache: provider- or runtime-level reuse of KV for shared system-plus-context prefixes; pays on long-context RAG and agent loops where the prefix dwarfs the turn -- the runtime-side cousin of exact-match, and the reason long-context costs fall non-linearly with conversation length.
  • Artifact cache: embeddings per chunk hash (the RAG ingest dedupe from the RAG guide), summaries per source-hash, extractions per document-hash; the highest-leverage layer because artifacts outlive conversations and recompute costs dominate ingest budgets.

Correctness: the four invalidation laws

Cache entries are promises that the world has not changed; four changes break the promise and must invalidate or version: model or weight change (version in key, old entries age out), sampling parameter change (in key), context-affecting data change (artifact layers hash the source; exact-match cannot know -- accept staleness per TTL or add dependency hashes), and access-tier change (never cache across tiers: a cached answer computed with tier-A retrieval served to tier-B sessions is an authorization bug wearing a performance feature's clothing, the retrieval-authorization rule from the RAG guide restated at cache altitude).

Operations: hit rates, poisoning, and the watts ledger

When not to cache

Personalized generation where the prompt embeds session-private state you cannot key safely; agentic planning turns where repetition is itself the signal (caching a planner's exploratory calls hides loops you need to see in journals); and any response class under active evaluation (A/B prompts, regression suites -- cached answers make benchmark runs measure the cache). The rule of thumb: cache where repetition means redundancy; skip where repetition means information, because the journal's loop-detection and your eval harness both read the uncached stream, and a cache that starves them is a performance feature eating your instruments.
