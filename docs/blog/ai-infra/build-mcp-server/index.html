How to Build an MCP Server: From Tool Schema to Sandboxed Executor

How to build an MCP server from scratch: typed tool schemas, stdio and HTTP transports, sandboxed executors, cancellation semantics and verification-key pinning.

Scope: one tool, done properly

We build a single-tool server -- verify_proof -- because every multi-tool server is this one tool plus a registry. The tool accepts a proof blob and a pinned verification key, returns a boolean plus metadata, and never executes anything the caller supplied beyond data. That restriction is the design: servers that "run what the agent sends" are not tools, they are remote shells with extra steps. The production sibling of this tutorial is mcp-prove-server, which adds prove-side tools under the same discipline; the pillar MCP tutorial covers the protocol landscape this guide assumes.

The schema: bounded, closed, self-describing

Three decisions to steal. The proof field's pattern doubles as validation and as documentation of encoding (base64url, not "base64-ish"). The vkey is a hash, never key material -- the server keeps an allowlist of pinned keys and refuses unknown ones, which converts "verify this" into "verify this against a program I recognize". And additionalProperties: false means a model hallucinating a timeout field gets a typed rejection it can learn from, instead of silent ignoring that teaches it nothing.

The executor: ceilings, tmpdirs, and data-only outputs

Execution runs in a child process with memory and CPU ceilings, a private tmpdir, and no network. Results return as plain data: { ok, verified, vkey, ms }. Never return file paths the child created (they vanish with the tmpdir), never return stderr blobs as success text (stack traces become prompt content), and always enforce a wall-clock budget the parent imposes -- a child that ignores its own timeout still dies when the parent's does.

Lifecycle: negotiate, notify, cancel, err structurally

At initialize declare only tools; read the host's capabilities and store them -- a host that cannot handle structuredContent gets the plain-text fallback. When your tool registry changes, emit tools/list_changed; hosts cache aggressively and stale caches produce calls to tools you no longer serve. Handle notifications/cancelled by killing the child and freeing the tmpdir immediately: cancelled provers that finish in the background are how a "stateless" server develops mysterious CPU debt. Errors return as tool results with isError: true and a one-line typed reason plus a correlation id; the full stack goes to your journal, not to the model.

Tests: the four classes that make it infrastructure

  • Schema fuzz: 10k generated inputs including 5 KB proofs, unicode junk, and nested objects -- assert typed errors, zero crashes.
  • Lifecycle: cancel mid-verify, close mid-batch, reconnect with stale list -- assert cleanup (no tmpdir leaks, no orphan children).
  • Policy: unknown vkey rejected; oversized proof rejected with the size echoed; journal gains exactly one line per decision.
  • Conformance: handshake against two host SDK versions; assert protocol-version negotiation and graceful refusal of unknown majors.

Wire all four into CI on every commit. The gate that runs in CI is the gate that runs in production; everything else is a demo with dependencies. Add one more cheap habit: a startup self-check that re-validates the pinned vkey allowlist and executor ceilings against the deployed policy file, failing loudly at boot if they disagree -- misconfiguration caught at deploy time is an event, at attack time it is a headline. Log the self-check's result to the journal as the session's first line, so every audit begins with evidence that the gates were alive before traffic arrived -- a one-line habit that has ended more than one "was the policy even loaded?" argument in its first minute. When your server passes these, the safety story in the APG-1 specification becomes enforceable at your boundary rather than aspirational in someone's threat model -- and the agent on the other side gets exactly what the protocol promised: an attestation, never a shell.
