Local RAG Pipeline Setup: Chunking, Indexes, and Honest Evaluation

A local RAG pipeline setup: chunking strategy, embedding choices, index sizing, retrieval evaluation with real queries and the failure modes that fake good scores.

The pipeline, component by component

  • Ingest: format extractors (markdown, PDF with layout-aware tools, code via tree-sitter splits), normalized to text plus metadata (source path, mtime, owner).
  • Chunk: 300-700 token windows with 10-15% overlap for prose; structural splits for code and docs (functions, sections) beat fixed windows wherever structure exists.
  • Embed: a local embedding model sized to your hardware (the 300M-1B class runs on CPU at ingest-time patience); embeddings versioned per model so re-embedding is a scheduled job, not a surprise.
  • Index: HNSW in-process for small corpora (under ~1M chunks), Qdrant/Weaviate-class when filters and multi-tenancy arrive -- the comparison lives in the cluster's vector-db shelf.
  • Retrieve: dense top-k (k=6-10) merged with BM25 keyword results (reciprocal-rank fusion), metadata filters first (project, date, access tier).
  • Generate: context assembled with chunk ids inline; prompt requires citations by id and forbids answers beyond retrieved content for fact-mode queries.

Quality: the eval loop that precedes tuning

Build a 50-100 query eval set from real questions (support tickets you wished auto-answered, your own search history), each with gold chunk ids and a one-line gold answer. Metrics per configuration change: retrieval recall@k (did gold chunks surface), citation precision (did the model cite what it used), and groundedness (judge-model score plus human spot-checks on twenty). Tune in order of leverage: chunking shape first (recall moves most), then fusion weights, then k, then prompt wording last -- the reverse order is how teams spend weeks polishing prompts over broken retrieval, the RAG equivalent of benchmarking the wrong workload per the benchmark discipline.

Citations: the trust architecture

Operations: ingest as a service, not a script

Continuous ingest watches sources (filesystem events plus nightly full sweeps), dedupes by content hash, and re-embeds only changed chunks; a quarantine queue holds extraction failures and oversize documents for human triage rather than dropping them silently. Access tiers travel in metadata and the retriever filters by session capability before similarity -- retrieval-time authorization is the only place it composes correctly with ranking, because post-retrieval filtering re-ranks nothing and leaks existence information into k. Monitor four numbers: ingest lag, quarantine depth, retrieval recall on the eval set (regression alerts), and citation-drift flags; the agent journaling Q&A's philosophy applies unchanged -- pipelines without heartbeats fail quietly, and quietly is how trust dies.

Honest limits, stated upfront

Start smaller than feels serious: twenty documents, fifty queries, one box. The pipeline's architecture does not change at a hundredfold scale -- chunking discipline, eval loop, citations, authorization-at-retrieval all survive contact with growth -- which is precisely why starting small costs nothing but pride and teaches everything but vendor lock-in -- and twenty documents later, the fifty-query eval set still governs every decision, exactly as designed.

When should I skip RAG and fine-tune instead?

When the knowledge is stable, style/format is the goal, and citation is unnecessary -- fine-tuning shapes behavior, not facts. When answers must track changing documents or carry provenance, RAG wins by construction. Hybrid (tuned style plus retrieved facts) is the mature answer for support bots; the decision rule is provenance: if users must be able to ask "where did this come from", retrieval is not optional, and no amount of tuning manufactures citations it never saw.
