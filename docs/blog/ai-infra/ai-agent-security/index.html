AI Agent Security Best Practices: Capabilities, Journals, Proofs

AI agent security best practices: capability gates, deny-by-default networks, append-only audit journals, signed receipts and the review loop that keeps gates honest.

The threat model in one diagram of words

An agent is a program whose control flow is partly written by untrusted text: user prompts, fetched web pages, tool outputs, and file contents all become instructions to a stochastic interpreter. The attack surface is therefore every byte the agent reads, and the primitive is injection -- text that says "now delete/ exfiltrate/ ignore previous". Consequences scale with capability: a chatbot with no tools can only say harmful things; an agent with shell, filesystem, and network can do harmful things at machine speed with your credentials. The capability-gates paper formalizes exactly this inversion: traditional security assumes the principal knows what it is doing; agent security must assume the principal can be rewritten mid-session by whatever it reads next.

Gates: deny by default, most-specific wins

The grammar's power is testability: 214 recorded agent-behavior cases run against every policy change in CI, so "the gate holds" is a checked property rather than a hope -- the suite and grammar are public in agent-policy-kit and specified normatively in APG-1. Operational rules that keep gates honest: policies live in Git with review like code; denials return typed reasons the agent can plan around (and attackers learn nothing from); and a deny-rate dashboard alerts on spikes, because sudden deny storms mean either an injection campaign or a policy regression, and both deserve a human within the hour.

Sandboxed executors: ceilings as architecture

When a gate grants execution, the executor enforces physics: child processes with memory and CPU ceilings, per-session tmpdirs deleted on close, egress-deny by default with per-tool exceptions, and outputs returned as data never as executable content. The MCP server guide's executor principles generalize beyond MCP: any tool the agent calls should run inside ceilings the agent cannot raise, because "the model promised it was safe" is not a control. Defense in depth here is not paranoia but arithmetic: gates fail at policy rate (text tricks), sandboxes fail at physics rate (cgroups, namespaces), and the intersection of two independent failure probabilities is the number your risk register should carry.

Journals: append-only, hashed, reviewed

Every decision -- grant, deny, needs-approval -- lands in an append-only journal with timestamp, session, tool, capability, verdict, latency, and prompt-hash. Three uses compound: incident review becomes a query rather than an excavation; policy tuning gains deny-rate and grant-pattern telemetry that no benchmark substitutes; and proof-carrying extensions (hashing journal segments, signing them, eventually attaching STARK receipts of gate evaluation per the research agenda) turn "the gate was applied" from assertion into verifiable claim. Retention follows data-protection logic: metadata long, prompt bodies short or never, scrubbing pipelines documented -- the journal proves behavior without becoming the leak it exists to police.

Staged rollouts and the human gate

New tools and policy widenings enter through observation: first week logs-only (the gate would-deny but reports instead of blocking), second week blocked-with-approval (a human answers needs_approval promptly, and promptness is measured because slow approvals train users to route around gates), third week autonomous within scope. Each stage exits on metrics -- would-deny patterns understood, approval latency under SLA, zero unexplained grants. The process sounds bureaucratic until you watch it catch the classic: a tool whose schema allowed path traversal that nobody noticed because the model never tried; observation weeks exist precisely because models explore less than attackers do, and your rollout should assume the difference is temporary.

Beyond the walls: supply chain and model provenance

Agent security ends where your supply chain begins: MCP servers and tool packages are dependencies with executive power, so admit them like contributors -- pinned hashes, reviewed code, minimal scopes, egress-deny at runtime regardless of vendor reputation. Model artifacts get the same treatment (hash-pinned weights per the privacy piece's practice), because a swapped model is a swapped principal. The unified rule across all layers: every component with executive power carries identity (hash), scope (policy), and record (journal). Systems that enforce the triad survive the inevitable injection that lands; systems that skip one layer discover which one they skipped during the incident, which is the most expensive possible way to learn an architecture lesson.

Do guardrail models or classifiers replace gates?

They complement, never replace: classifiers detect injection attempts with useful but imperfect accuracy, while gates enforce capability boundaries deterministically. Use classifiers to raise approval thresholds on suspicious sessions (adaptive friction), and gates to make the worst case bounded regardless of classifier verdicts. A classifier-only design bets the estate on a model's mood; a gate-only design misses context -- together they price risk where it belongs.

How do I secure agents that must browse the web?

Treat fetched content as hostile input by construction: render-free fetchers (text extraction only), egress scoped to allowlisted domains where possible, and zero write-capabilities in the same session as unbounded browsing -- the classic exfiltration channel is a read-capable agent that also holds write or network grants. Split sessions: a reader session summarizes untrusted pages into a sanitized brief; a writer session acts on the brief with gates. Two principals, one workflow, no single session holding both halves of the exfiltration primitive.

What is the first gate to add to an existing ungated agent?

Network egress deny plus filesystem read-only, granted upward per demonstrated need -- it collapses the exfiltration and destruction classes immediately while leaving most legitimate workflows merely inconvenienced (approvals for the exceptions). Measure the approval queue for a week: it is both your usability budget and your attack-log sample, and it hands you the empirical basis for every subsequent grant, which is how policies grow from evidence instead of anxiety.
