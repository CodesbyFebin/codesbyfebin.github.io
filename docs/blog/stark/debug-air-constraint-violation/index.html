How Do I Debug an AIR Constraint Violation in a Large Trace?

How to debug AIR constraint violations fast: bisecting traces, flag-column assertions, first-failing-row dumps and the four patterns behind most unsound constraints.

Step 1: name the failing row and constraint

Winterfell-style provers fail loudly but globally ("constraint evaluation nonzero"); your first job is locality. Instrument the AIR in a debug build to record, per row, which constraint index deviates and by how much; stop at the first deviation. The row index is your timestamp: convert it to a cycle, map the cycle to source via the executor's step log, and you have the exact instruction where legality broke. Skipping this step and re-reading constraints top-down is the classic hour-waster -- constraints are specifications, and debugging by re-reading specifications is debugging by horoscope.

Step 2: check the usual suspects, in order

  • Padding rows. Idle rows must satisfy every transition with flags zero; a constraint missing its flag multiplier wakes up only in the pad region -- deviation row ≥ real cycle count is the signature.
  • Flag encoding drift. Executor sets flags from opcodes; a refactor that renumbers ops but not flag columns produces legal-looking rows that violate semantics at specific opcodes.
  • Jump off-by-ones. pc relations assume fallthrough +1; immediate-base confusion (relative vs absolute) deviates exactly at taken jumps.
  • Unbound column drift. A column constrained only conditionally can wander on other rows; deviation appears where the next conditional use reads the drifted value -- run the column census from the AIR article when the frame looks "fine" yet constraints disagree.

Step 3: bisect the trace, not the code

When the failing row's instruction looks innocent, the bug is upstream: re-run the executor with half the inputs, then quarter, watching whether the deviation row survives -- trace bisection localizes causal chains (a corrupted register written fifty cycles earlier) that row-local inspection cannot see. Pair with the differential executor (independent interpreter recomputing columns) from the trace article: where its columns and yours diverge is where your executor lied, and where both agree but constraints deviate is where the AIR lies. Two witnesses, one intersection -- the method generalizes the drift-matrix thinking from the verification Q&A from parameters to semantics.

Step 4: freeze the bug as a test before fixing it

My constraints pass but the prover still rejects -- where next?

Leave semantics and check geometry: boundary assertions (first/last row pins), auxiliary column initialization (permutation products must start at identity), and padding length versus declared trace size. These live outside transition evaluation and are the usual home of "constraints green, proof red" -- the parameter half of the drift matrix in the verification-failure Q&A covers the remaining cases.

Can I get the prover to print violating rows directly?

In debug builds, yes -- wrap constraint evaluation with a recorder as shown above; never in release, since the recording closure costs more than proving at scale. Keep the recorder behind a feature flag with a test asserting the flag changes nothing mathematically (same proofs with flag on), so debuggability never becomes a soundness variable.

How do I debug violations that appear only at large trace lengths?

Length-dependent deviations are almost always padding or boundary interactions: reproduce at the smallest power-of-two above the failure threshold with synthetic inputs, then shrink inputs until the deviation vanishes -- the last reproducing size brackets the padding boundary. If the bracket is empty, suspect degree-related composition overflow at scale and re-check field size against constraint degree times trace length, the arithmetic the security-parameter manifest exists to keep honest.
