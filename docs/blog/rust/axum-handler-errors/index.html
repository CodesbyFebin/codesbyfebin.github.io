How Do I Return Clean Errors From Axum Handlers?

How to return clean errors from axum handlers: IntoResponse impls, typed error enums, status mapping, logging hooks and consistent JSON error envelopes.

The enum: statuses as variants, codes as contract

The envelope's fields are a contract with distinct owners: error strings are semver-surface (clients match on them), message is prose free to improve, request_id joins your trace layer so support conversations start with a lookup. Internal context (the anyhow chain) goes to logs only -- leaking library error text into responses is how internals become attacker vocabulary, the same boundary discipline the error-strategy guide draws between libraries and binaries, here drawn between server and wire.

From implementations: where conversion lives

Each library error type gets one From into ApiError at the boundary module, mapping semantics not strings: a proof verifier's VkeyMismatch becomes ProofRejected with the expected hash in the message; IO becomes Upstream with context logged. Handlers then use ? everywhere and read like the happy path -- the error architecture's entire job is making the sad path invisible in business logic while remaining explicit in one reviewed file. Resist the temptation to impl From<anyhow::Error> broadly: it collapses every future library error into one variant, destroying the status semantics you just bought; convert named types only, and return an internal error for unexpected failures and log the cause with a request id, because an unexpected error deserves an alert, not a polite envelope.

Extractor rejections: the envelope's other entrance

Invalid JSON and failed path parsing arrive as rejections before your handler runs, carrying axum's default bodies. Unify them with a HandleError layer or a custom rejection type mapping to ApiError::Validation with field-level issues extracted where available; clients then parse one envelope for every 4xx regardless of which layer objected. Test the matrix: malformed body, wrong type, missing field, oversize body (your body limit's 413 joins the envelope too), and wrong method (405) -- five cases, one shape, zero client-side special cases. The axum tutorial's fallback section closes the remaining door (unknown paths), completing the property that makes SDK generation and client error handling boring: every response, everywhere, one grammar.

Testing the error contract like a public API

  • Per variant: assert status, code string, and envelope keys via portless Router::call requests (the tutorial's testing pattern).
  • Per rejection class: the five-case matrix above, including oversize and method mismatches.
  • Contract freeze: a golden-file snapshot of envelope shapes (not messages) so accidental code-string changes fail review loudly.
  • Log join test: assert request_id in body equals the id in the captured log line -- the support workflow is part of the contract.

Error contracts drift silently faster than success contracts precisely because nobody exercises them happily; these four test classes are the happiness substitute. Teams that adopt them report the same surprise every time: the error tests catch more real regressions than the success tests, because errors are where layers meet -- and layers meeting is where systems actually live, in axum as in the federation control planes that inspired the envelope design in the first place.

Should 500s carry any detail at all?

A code ("internal"), a message ("unexpected error; request id attached"), and nothing else. Details belong in logs keyed by request_id; response detail is reconnaissance donated to attackers. The one exception worth debating: staging environments echoing sanitized chains behind an auth gate, which accelerates debugging without enlarging the production surface -- gate it, label it, and never let the flag ship default-on.

How do I version error codes without breaking clients?

Additively only: new codes may appear, existing codes never change meaning or spelling; deprecations happen by adding a successor code and logging both for a transition window. Clients matching unknown codes must fall back to status-class handling -- document that expectation in your API guide, because a client that hard-fails on unknown codes has converted your additive change into their outage, and the fallback rule is the treaty that prevents it.

Is a string code better than a numeric one?

Yes, for APIs humans debug: "proof_rejected" survives log greps, ticket titles, and memory; numeric codes save bytes nobody spends over JSON. Reserve numbers for protocol-level economy (binary protocols, embedded clients) and keep the string-to-number table generated if both worlds must coexist -- generated tables cannot drift, which is the only property that makes dual vocabularies survivable.
