Anatomy of an error, top to bottom

The spans are the compiler's proof sketch: where the borrow begins, where the conflict occurs, and where the borrowed value is still needed. Ninety percent of borrow errors resolve by reading those three in order and asking which is wrong about your intent -- the borrow starting too early (narrow the scope), the use lasting too long (clone or copy the needed datum), or the mutation belonging elsewhere (redraw ownership). Skipping to "apply suggestion" without the read is how teams accumulate clones they cannot explain, the clone-debt pattern the E0505 Q&A catalogs from the other side.

Tooling that turns messages into navigation

  • rust-analyzer inlays: borrow regions and inferred types visible before compilation -- half of borrow errors die as you type.
  • cargo explain: cargo explain E0502 gives the rule's essay with canonical examples; read once per code, not once per error.
  • --error-format json in CI: errors as data, enabling trend dashboards (which codes recur, which crates breed them) -- recurring codes are training agenda, not individual failures.
  • RUST_BACKTRACE and -Z macro-backtrace: when the span points inside a macro, the backtrace names the macro invocation chain that hid the truth.

Teaching readings: the mentor's sequence

Are some error codes worth memorizing outright?

Five cover most daily life: E0382 (moved), E0502/E0505 (borrow conflicts), E0499 (double mutable borrow), E0716 (temporary dropped while borrowed). Memorize their shapes, not their numbers: use-after-move, immutable-mutable overlap, mutable-mutable overlap, and dangling-into-temporary. Every other code becomes lookup-able once those four mental models exist, because the rest are specializations of the same ownership geography.

What when the compiler is actually wrong?

Rare but real (usually inference edge cases or diagnostics mislabeling): reduce to a minimal repro, check against current nightly and the issue tracker, and file or link the existing issue in your design note with the workaround chosen. Treating compiler bugs as documented dependencies -- workaround, tracking issue, revisit schedule -- is the professional shape of "the tool is wrong", and it keeps teams from carrying private compiler folklore that new hires cannot look up.

Do suggestions differ between stable and nightly?

Yes: nightly diagnostics ship improvements months early (better borrow-region prints, new lints), which is a reason to keep one nightly job in CI for diagnostic preview -- not for features. Reading tomorrow's diagnostics today sounds like vanity until the week a confusing stable message costs an hour and the nightly phrasing already taught you the model; diagnostics are part of the toolchain you deploy, and toolchains deserve staging like code does.
