Rust Traits vs Generics: Dispatch Costs and API Design

Rust traits vs generics: static versus dynamic dispatch costs, monomorphization bloat, object safety rules and how to design APIs that stay fast and flexible.

What the machine actually does

The other two budgets: bytes and compile seconds

Monomorphization's bills arrive elsewhere: binary size grows per instantiation (a generic over five types ships five copies -- visible via the bloat workflow in the size Q&A), and compile time grows superlinearly as downstream crates instantiate your generics anew. Dynamic dispatch pays once: one vtable, one body, stable compile times as consumer types multiply. This inversion is why plugin systems, serializer registries, and service handler tables classically use dyn: heterogeneous collections (Vec<Box<dyn Handler>>) are simply inexpressible with generics alone, and compile-time economics favor erasure precisely where type diversity is the feature rather than an accident.

API design: generics inward, objects at borders

Measuring the close calls

  • Micro: criterion benches of the hot kernel in both styles; deltas under 3% mean the decision belongs to the other budgets.
  • Binary: size diffs per style via the bloat workflow; embedded and CLI targets weight this heavily per the size Q&A's ledger.
  • Compile: cargo build --timings on a downstream consumer crate; generic-heavy libraries show up in other people's CI minutes, a cost your README never mentions and your users never forget.
  • Profile: when in doubt, flamegraph both -- indirect-call plateaus with thin frames are dyn's signature; duplicated towers of identical logic are monomorphization's.

A closing heuristic for library authors specifically: expose generics where your docs can name the concrete types users will instantiate (collections, parsers, serializers), and expose objects where the docs cannot (handlers, plugins, user extensions). The distinction tracks extensibility ownership -- closed type sets are yours to monomorphize, open sets are your users' to erase -- and following it keeps both your binary sizes and your contributors' compile times inside budgets that neither side negotiates consciously, which is exactly how good defaults earn their keep: invisibly, quarterly, forever.

If your codebase already mixed both styles without policy, the remediation order is: inventory dispatch sites with the bloat and timing tools, classify each by its binding budget, and migrate only the sites where the wrong style costs a measured resource -- style consistency for its own sake is a refactor, while budget-driven migration is engineering, and the distinction keeps reviewers on your side through the quarter it takes.

Is impl Trait in argument position just generics?

Syntactically yes (desugars to a generic parameter), with one practical difference: impl Trait arguments cannot be turbofished or named in docs as cleanly, and multiple impl Trait args cannot express relationships between types ("both the same T") -- where relationships matter, write the generic bound explicitly. Readability at the signature is API design; choose the spelling your callers will understand at 2 a.m., not the shortest one.

Does dyn Trait hurt async code differently?

Yes, mildly: async trait objects need boxing or the async-trait desugaring (allocated futures) unless you use native async-fn-in-trait support with its Send-bound caveats; the allocation per call is usually noise beside IO, but in per-packet paths it shows. Hot async kernels often prefer enum dispatch or generics for exactly this reason -- the vtable is not the cost; the heap is.

When is enum dispatch wrong?

When the variant set is open across crate boundaries or plugin loads: every consumer recompiles per new variant, and the "closed" set grows teeth via feature-flag sprawl. The test is organizational as much as technical -- if adding a type requires editing a shared enum in a repo you do not own, you have a plugin system pretending to be a match statement, and dyn (or a registry of dyn) is the honest shape.
